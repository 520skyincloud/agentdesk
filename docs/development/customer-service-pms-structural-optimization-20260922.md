## 2026-09-24 JEV 上下文与回复性能实施记录

本轮目标是解决客户短回复无法承接、上下文持续膨胀以及已确认答案仍重复调用 Generate 的
产品问题。改动仅涉及：

- `internal/ai/runtime/executor/jev_intent_detector.go`
- `internal/ai/runtime/executor/intent_runlog_context.go`
- `internal/ai/runtime/executor/service.go`
- 对应 executor 测试

实施结果：

- 单目标消息在一次 JEV 请求中同时完成目标数量判断与分类；多目标消息继续使用原边界协议。
- JEV 输入限制为最近八条有界历史，并使用“原始业务目标 + 最近两条去重补充”的快照，避免
  `resolvedText` 在连续追问中递归增长。
- “放在哪里”“1501”“上面那个”“不是这个”等短回复，只有在 JEV 明确选择最近业务 Task，
  且关系属于追问、选择、确认、纠正或不满时，才继承上一业务路由；完整新主题保持独立。
- 独立招呼或闲聊成为旧主题屏障；对上一答复的拒绝和不满继续保留当前业务目标。
- 历史消息进入 JEV 前剥离内部展示标签；同一来源且指向同一订单对象的房型、房号、入住、
  退房等字段合并为一个复合 Task，避免两次 PMS 查询和两条相同失败回复。
- 完整的 Judge 知识答案和完整的 PMS + 知识多 Task 答案通过发送安全后直接 Commit，减少
  一次 Generate 往返；缺失事实、资源、人工、待调用工具及不安全结果不进入快路径。

本轮没有修改 model、Migration、DTO、enum、路由、WebSocket、数据库、外部 API、企微协议、
计费、Outbox 或 PMS 配置；HPMS 仍为只读，写操作保持关闭。并行分支检查结果：
`origin/codex/customer-audit` 与 `origin/codex/ai-billing` 未修改本轮三个运行文件，无需约定
额外合并顺序。回滚只需切回上一程序 release，不恢复数据库，也不触碰“薇薇/薇薇2”备份。

验证记录：executor 连续两轮、services、runtime、PMS 和 pkg/utils 回归均通过；真实 JEV
15 个场景通过，包含“房型 + 退房时间”复合订单追问，单问题意图调用约 0.4-1.4 秒，六问题
约 2.6 秒。首次隔离 PMS 冒烟所用手机号在 HPMS 中确实不存在，不能据此判定上下文失败；
使用其风测试订单手机号直查时接待单接口正常返回。最终线上会话验收需在部署后检查咖啡位置
追问、订单退房追问、房型选择后询价、PMS 与停车混合问题及明确人工五类场景，并核对回复
自然度、上下文长度、内部信息泄漏、重复索要手机号和投递耗时。

## 0. 2026-09-23 实施收口

本轮已按下述结构方案完成运行代码修改，尚未改变数据库结构、外部 API、企微协议、
Outbox 或 PMS 数据。关键落地结果如下：

- 同一会话最近一次成功且真实发送的 PMS Task 可以复用手机号和真实订单定位；复用严格
  限定同会话、同 Agent、同 session，并要求 PMS 工具成功、Task 含 PMS 事实且消息状态为
  `sent`。当前消息出现新手机号、否定或纠正时始终覆盖旧定位。
- 续住评估同时读取预订单和接待单；支持“多住一晚、续一天、续两天、再住2晚”等机械
  日期派生，并按旧离店日、目标离店日和当前房型查询库存。运行 allowlist 不包含 `renew`，
  全流程保持只读。
- PMS 部分查询成功时保留已确认事实；目标房型、日期或价格依据缺失时只追问对应字段，
  不把整个 Task 改写成通用失败，也不猜目标房型。
- 客户明确拒绝人工时，维修问题保留“需要同事处理、当前不转接、可登记维修工单”的真实
  能力边界，不自动建单、不虚报完成。
- JEV 对合法逆序边界按原文位置机械排序；重复或非法边界最多重试一次，不新增第二个拆题器。
- Judge 首次超时后可在原 45 秒总预算内执行一次同协议紧凑恢复：主调用 33 秒，恢复 12 秒；
  恢复只缩小候选数量，不改变任务、语义裁决职责或协议。两次失败仍安全失败，最终超时保持
  `timeout`，不会被覆盖检查误写为 `coverage_failed`。
- Generate 或 Validate 的全局失败只在唯一未提交文本 Task 时允许恢复，避免把一个 Task 的
  故障错误绑定到已经成功的相邻 Task。
- HPMS 同一预订单可返回多条接待单。预订单 ID、日期区间和真实房型一致时，可共享订单级
  离店日、房型等只读字段继续查库存；房型同时读取实际响应中的 `roomId`。需要接待单 ID 的
  查询仍保持歧义，不任意选择房间。
- Executor/Judge 已形成的非空固定答复不再交给 Generate 重写；模型协议失败时仍原样保留
  维修拒绝转人工等已确定结果。
- 续住只读评估以预订单离店日、当前房型和目标日期库存为必要事实。接待单与换单候选是增强
  信息，查询失败不覆盖已确认结果；库存完整性和客户回复均只针对当前绑定房型，不因其他
  房型缺少逐日库存而误报续住资料不足。
- 客户级“关闭自动转人工”只约束普通自动升级。客户当前明确要求人工、知识库明确要求转接
  及安全风险是独立授权入口，不得被该设置拦截；非明确投诉、服务请求、PMS 失败和知识不足
  仍继续自助回答或追问，不能自动转接。

自动验证要求为普通测试连续两轮、竞态测试连续两轮；部署后再对每类真实客户需求至少使用
两种问法验证。最终发布身份与线上验证结果写入 `docs/development-handoff.md`。

## 1. 目标

这次不是继续给“升房”“外卖”“手机号”各补一条特殊规则，而是修正现有链路中四个职责错位：

1. 客户已经提供并用于成功查询的手机号、订单和入住区间，应在同一会话业务主题内继续使用。
2. 客户表达实际需求后，系统应按业务目标完成必要的 PMS 查询步骤，而不是把一个通用 `pms_query` 工具交给 Generate 自由猜调用顺序。
3. 知识库已经召回的直接答案必须真实进入 Judge，Judge 选中后必须稳定进入回复；排障日志必须能准确说明答案在哪一步丢失。
4. 每个 Task 应独立形成“答案、必要追问或明确的局部失败说明”，不能因为一个子查询失败而把整轮回复替换成“暂时没法准确回答”，也不能因此自动转人工。

最终链路仍保持：

```text
消息收敛
→ JEV Intent/拆题
→ 复用已确认业务定位信息
→ 按 Task 生成确定性查询计划
→ PMS 只读查询 / 知识检索
→ Judge 只裁决知识证据
→ 汇总 Task 事实
→ Generate 组织自然回复
→ Commit
→ Outbox
```

不新增平行 Agent，不新增第二套回复状态机，不新增“已回答题目”状态，不新增通用本地语义检测器。

## 2. 非目标

- 本轮不开放 HPMS 写入，不执行升房、换房、排房、延迟退房、续住、改价或锁房。
- 不把“可售”描述成“已锁房”或“已经办理”。
- 不新增知识内容来掩盖检索或 Judge 问题。
- 不改企微协议、消息表、Outbox、计费、外部 API 或后台页面。
- 不回退或修改“薇薇”“薇薇2”备份。
- 不用关键词补丁为某一句客户原话写固定回复。

## 4. 本质原因

### 4.1 已确认业务信息没有进入可复用上下文

当前 PMS 必填槽位预检只检查当前 Task 的：

- `Text`
- `ResolvedText`
- `Entities`

JEV 可以从最近历史选择一个客户 Task 来补全当前问题，但它不能稳定表达：

```text
这个手机号已经成功定位了当前订单，后续“这笔订单”“上面那个”“我最晚几点退房”继续使用它。
```

同时，JEV 的历史选择只能选一个先前客户文本。一次升房追问可能需要同时继承：

- 更早提供的手机号；
- 最近讨论的订单；
- 当前目标房型；
- 订单的入住和离店日期。

因此“看到了历史”不等于“拥有可复用的业务定位信息”。

### 4.2 `needsTool=true` 只表示工具可用，不表示业务查询会完成

目前 PMS Task 进入 Generate 后，模型自行决定：

- 先查预订单还是接待单；
- 是否再查详情；
- 是否把订单日期传给库存；
- 是否根据库存返回的真实房型 ID 继续计算差价；
- 是否查询会员权益；
- 一个子查询失败后是否继续使用其他结果。

这使同一个 `room_upgrade` 在不同轮次可能只查订单、只查库存，或者查了会员却没有查差价。工具本身可用，但业务目标没有完成契约。

### 4.3 工具参数契约只做白名单，没有按业务目标检查必要字段

例如 `inventory` 支持 `beginTime/endTime`，但当前工具 Schema 只要求 `action`。模型只发送：

```json
{"action":"inventory"}
```

请求仍然会发到 HPMS，HPMS 可能按默认营业日返回数据。客户问的是 9 月 23 日到 9 月 24 日，回复却可能使用 9 月 22 日库存。

这不是模型“回答能力差”，而是缺少机械的操作参数契约。

### 4.4 PMS 结果没有形成 Task 级事实汇总

当前工具调用结果作为模型上下文存在，但没有统一的 Task 结果结构区分：

- 已确认订单事实；
- 已确认目标房型；
- 已确认完整入住日期库存；
- 已确认会员权益；
- 已确认精确差价；
- 未确认的方面；
- 某个子查询失败但其他子查询成功。

因此一个接口失败后，Generate 容易把整个 Task 处理成通用失败。

### 4.5 当前房型、目标房型和营销房型名没有严格分离

“我想换大床房”中的“大床房”是客户目标描述，不是当前订单房型。

当前回复曾把目标描述写成当前订单房型，并把“星旗房”等 PMS 名称混在一起。原因是三个字段没有单独建模：

```text
currentRoomType       PMS 当前订单真实房型
requestedRoomTypeText 客户原话中的目标描述
targetRoomType        PMS 库存中唯一匹配的真实目标房型
```

如果目标描述不能唯一匹配 PMS 房型，应展示实际可选房型或追问一次，不能猜 ID，也不能反过来修改当前房型事实。

### 4.6 外卖问题的排障信号不准确

当前 Retriever 日志在 Judge 执行前写入，`UsedHits` 此时为空，因此原始命中会统一显示：

```text
context_limit_or_duplicate
```

这个标记不能证明候选真的因为长度或重复被丢弃。真正需要核对的是：

```text
RawHits
→ 进入 Judge 的 Candidate IDs
→ Judge 选择的 Candidate IDs
→ 最终事实与 answerText
```

现有代码虽然优先从 `RawHits` 构建 Judge 候选，并给普通 Task 三个候选额度，但当前 trace 没有把上述四步清楚串起来。因此目前可以确认：正确知识已经被召回，但不能仅凭 `context_limit_or_duplicate` 断言它在哪一层丢失。

结构性修复必须先让这条证据链可观测，再根据真实 Candidate ID 判断：

- 未进入 Judge：修候选选择；
- 进入 Judge 但判不足：修 Judge 的当前问题/候选契约；
- Judge 已选中但未回复：修 Task 事实汇总或 Generate。

### 4.7 JEV 的 Task 边界与业务办理目标没有完全对齐

JEV 当前规则倾向把“有房吗”“会员免差价吗”“要补多少”视为不同答案目标。这对普通多问题有帮助，但对“能否升房”会产生多个重复 `room_upgrade` Task，并让每个 Task 重复调用相同查询、重复回复。

升房、换房、续住、延退属于一个客户决策目标，库存、会员、价格和政策是完成该目标的必要判断维度，不应都变成相同的独立办理 Task。

### 4.8 服务请求只有“知识答案”与“人工”两端，缺少正常处理结果

例如：

```text
空调不制冷，我住 1401，先告诉我可以怎么处理，不要转人工。
```

当前分类为 `maintenance` 并查知识。如果知识不足，没有进入现有维修工单能力，也没有产生清楚的局部说明，最终变成通用失败。

另一个例子：

```text
1401 房空调坏了，请帮我创建一个维修工单。
```

客户已经明确要求建单，但 JEV 只给出 `maintenance`，没有把 `action_request` 绑定到现有 `create_ticket_with_confirmation`。

### 4.9 通用失败话术掩盖了真实失败类型

“暂时没法准确回答”同时被用于：

- 缺少手机号；
- 日期没有传给库存；
- 没找到目标房型 ID；
- 某个接口失败；
- Judge 证据不足；
- 服务任务没有进入工单；
- Generate 漏答。

同一句话掩盖了完全不同的修复方向，也让客户不知道下一步需要提供什么。

## 5. 客户真实需求与自然问法

验收问题必须从客户目的出发，不能写成“调用库存接口”“测试会员接口”。

| 客户需求 | 自然问法示例 | 系统内部需要完成的事情 |
| --- | --- | --- |
| 确认订单 | “我今晚到店，帮我看看订单是不是已经生效了？” | 复用已有手机号或只追问一次，查询预订单和接待单 |
| 查询入住信息 | “我订的是哪种房？几点入住、几点退房？” | 定位订单并回答房型、房号、日期、状态 |
| 连续追问 | “那我最晚几点退房？” | 复用上一笔订单，不重复问手机号 |
| 修改手机号 | “刚才号码说错了，用这个号码重新查。” | 立即使旧号码失效，使用新号码 |
| 查看房间状态 | “我到门口了，1401 现在打扫好了吗？” | 查实时房态，只回答当前状态 |
| 查看未来库存 | “我明晚还想住一晚，还有什么房型？” | 使用客户日期查询库存，不能使用默认当天 |
| 升房评估 | “这个房间有点小，能换个大床房吗？大概要补多少？” | 当前订单、目标房型、完整日期库存、会员权益、差价 |
| 会员升房 | “我是你们会员，换好一点的房型能免差价吗？” | 订单、会员等级、明确权益、目标房型库存和价格 |
| 换房评估 | “房间临街有点吵，今晚还有别的房能换吗？” | 当前接待单、当晚/剩余入住期库存、知识政策；不猜安静属性 |
| 延迟退房 | “我下午三点才走，可以晚点退吗？要收费吗？” | 当前订单、原退房时间、后续房态、门店政策 |
| 续住评估 | “行程改了，我想多住一晚，同房型还有房吗？” | 当前订单、目标日期、库存、续住候选 |
| 会员信息 | “我经常住你们家，我这个手机号是什么会员？” | 会员信息查询 |
| 会员权益 | “我这个会员有什么权益，生日有福利吗？” | 会员等级及实际权益查询 |
| 外卖机器人 | “外卖到了，机器人能送到房间吗？” | 检索外卖机器人知识并直接回答，不自动转人工 |
| 外卖地址 | “我点外卖地址怎么填？” | 检索门店地址知识 |
| 外部代办边界 | “你帮我点个外卖吧。” | 回答无法代点，同时提供已有外卖地址/方式知识 |
| 用品请求 | “房间拖鞋用完了，哪里还能拿？” | 直接回答用品知识，不先重复确认问题 |
| 维修咨询 | “空调不制冷，我住 1401，先告诉我怎么办。” | 先答知识；知识不足时说明并提供现有工单入口，不自动转人工 |
| 明确建单 | “1401 空调坏了，帮我建个维修工单。” | 绑定现有建单确认 Graph Tool |
| 明确人工 | “帮我转人工客服。” | 进入现有人工流程，只执行一次 |
| 混合问题 | “帮我看今晚订单，再告诉我停车从哪里进。” | PMS 和知识分别完成，按客户顺序回答 |
| 纠正答非所问 | “我问的是机器人能不能送上来。” | 绑定上一条失败 Task，重新回答该目标，不列主题菜单 |

## 6. 目标职责边界

### 6.1 JEV：只负责客户目标、Task 边界和上下文关系

JEV 应负责：

- 识别当前客户要解决什么问题。
- 区分新问题、追问、补充字段、纠正、取消和拒绝上一答案。
- 保留客户原话和来源。
- 区分普通酒店知识、PMS 只读评估、服务动作、明确人工。

JEV 不负责：

- 选择具体 HPMS 端点。
- 自由决定升房需要查哪些数据。
- 判断查询成功与否。
- 生成 PMS 事实。
- 代替知识 Judge。

Task 边界调整：

- 停车、外卖、订单等独立问题继续拆开。
- “能否升房 + 有没有房 + 是否免差价 + 补多少”作为一个升房决策 Task，内部包含多个必要事实。
- 客户明确只追问“差价多少”时，可以单独形成 `price_difference` Task，但复用前一升房目标和订单。
- 不通过本地关键词重新拆题；只调整 JEV 的 typed criteria 和示例。

### 6.2 Executor：把 Task 转成确定性查询计划

新增的不是判断模型，而是一个小型、可测试的业务查询计划器：

```text
Task.SubIntent
+ 已确认业务上下文
+ 客户当前明确字段
→ 必须执行的只读步骤
→ 每步必要参数
→ 每步成功/部分/失败状态
```

它只对已经被 JEV 分类为 PMS Task 的任务工作，不重新判断客户语义。

### 6.3 PMS Adapter：只负责真实接口、字段和安全边界

PMS Adapter 应负责：

- 端点、方法、参数白名单。
- `hotelId`、租户和认证由服务端绑定。
- Long ID、金额、空字段和业务错误处理。
- 客户侧字段投影与脱敏。
- 操作级必要参数校验。

PMS Adapter 不负责：

- 判断客户是不是在问升房。
- 判断是否转人工。
- 生成客户话术。

### 6.4 Judge：只裁决知识证据

Judge 只处理门店知识与通用知识：

- 哪些候选与当前问题直接相关。
- 知识回答是否完整或部分完整。
- 是否存在知识库明确的转人工指令。

PMS 成功结果不要求再经过 FAQ Judge，也不能因为没有 FAQ 被否决。

### 6.5 Generate：只组织已经确认的事实

Generate 输入必须已经包含 Task 级事实和缺失项。它可以把事实写得自然、简短，但不能：

- 决定还应该调用哪个 PMS 接口。
- 把目标房型写成当前房型。
- 把部分失败写成全部失败。
- 把可售写成已办理。
- 因一个子查询失败而自动转人工。

## 7. 手机号与订单上下文设计

### 7.1 不新增平行持久化状态

优先复用：

- 当前 session 的客户消息历史；
- 当前/近期 `AgentRunLog.TraceData` 中已完成的 PMS 调用；
- 当前 Task 的 `ResolvedText` 和来源；
- PMS 返回的订单 ID、入住区间和房型。

第一版不新增手机号状态表，不建立新的对话状态机。

### 7.2 定位信息优先级

```text
1. 当前消息明确给出的新手机号/订单 ID
2. 当前消息明确纠正后的新值
3. 同一 session 最近一次成功 PMS 查询使用的手机号和订单
4. 同一 PMS 主题中客户最近明确提供、尚未被否定的手机号
5. 都没有时，才追问一个关键字段
```

### 7.3 失效规则

以下情况使旧定位信息失效：

- 客户明确说号码错了、不是这个号码、不要用这个号码。
- 客户提供新的手机号并要求重查。
- 客户明确切换到另一位住客或另一笔订单。
- 当前 session 结束或会话进入新的 session。
- PMS 返回多笔无法唯一定位，且客户选择了另一笔订单。

普通新话题不会删除定位信息，但只有 PMS 相关 Task 可以使用，停车、闲聊等任务不能把手机号写进回复。

### 7.4 订单复用

手机号仅用于重新定位，不把旧订单数据永久当真。每次需要实时状态、库存、金额或退房时间时仍重新查询 PMS。

可复用的是：

- 查询条件；
- 最近唯一订单 ID；
- 客户当前讨论的订单主题。

不可复用为最终答案的是：

- 旧库存；
- 旧房态；
- 旧价格；
- 已经变化的订单状态。

## 8. PMS 只读查询计划

### 8.1 订单查询

```text
手机号/客户编号
→ reserve_order_by_phone + recept_order_by_phone
→ 按关联 ID 去重
→ 0 笔：说明当前条件未查到有效订单
→ 1 笔：建立当前订单上下文
→ 多笔：展示最小区分信息并让客户选择，不擅自选第一笔
```

接待单查询失败但预订单成功时，保留预订单事实，并只说明接待状态暂未确认。

### 8.2 订单详情

```text
当前订单 ID
→ reserve_order_detail 或 recept_order_detail
→ 返回客户明确询问的字段
```

字段完整性按客户问题检查：客户问房型、房号、入住、离店、状态五项，就必须分别给出五项或明确哪一项未返回，不能静默漏掉房号。

### 8.3 日期库存

`inventory` 的机械必要参数：

- `beginTime`
- `endTime`

日期来源优先级：

```text
客户当前明确日期
→ 当前订单入住/离店日期
→ 当前营业日（仅客户明确问“今晚/今天”）
→ 缺失时追问日期
```

不得无日期调用后把默认营业日结果回答成客户指定日期。

### 8.4 升房评估

```text
定位当前订单
→ 读取 currentRoomType、入住/离店日期
→ 按完整日期查询库存
→ 从 PMS 返回中唯一解析 targetRoomType
→ 查询会员权益
→ 有真实订单 ID、目标 roomTypeId 和价格字段时计算 price_difference
→ 合并为一个升房评估结果
```

结果至少区分：

- 当前订单房型。
- 客户目标描述。
- PMS 实际目标房型。
- 完整入住区间是否有库存。
- 会员是否有明确免费升房权益。
- 精确差价、预计差价或无法报价。

目标房型解析只允许：

- 客户原话与 PMS 返回房型名的规范化精确匹配；
- 当前上下文中客户已从 PMS 返回列表明确选择的房型。

不能唯一匹配时，直接列出真实可选房型让客户选择，不猜 ID。

### 8.5 换房评估

```text
定位当前接待单
→ 查询当前房间和剩余入住区间
→ 查询目标日期库存
→ 必要时查询当前房态
→ 查询门店换房/补救知识
→ 输出可行方案
```

现有接口没有专用“完整入住区间具体房号可分配”端点，但实时房态已经返回每个具体房间及其
预订单、在住单的入住/离店区间。因此当前实现按房间执行只读组合计算：

```text
实时房态 homeCardList
→ 排除锁房、维修房
→ 合并 reserveOrderInfoList/checkInOrderInfoList
→ 用 [checkInTime, checkOutTime) 检查完整入住区间冲突
→ 返回全程无冲突的候选 homeId/homeName
```

该结果不代表锁房或排房。客户自己的当前订单可从占用区间中排除；其他订单时间缺失、查询日期
超出实时房态未来约 30 天覆盖范围或 PMS 未返回完整房卡时，结果必须标记 `partial`，不能确认
具体房号。临街、安静、靠电梯等偏好不从楼层或房号推断，继续使用知识库。

### 8.6 差价评估

`price_difference` 已存在，但必须由查询计划调用，而不是期待 Generate 自行想到。

精确差价需要：

- 真实预订单或接待单 ID。
- 真实目标 `roomTypeId`。
- 完整入住和离店日期。
- 当前订单逐日价格。
- 目标房型逐日价格。
- 相同币种和相同计价口径。

缺失时返回 `quote_only` 或 `insufficient_data`，并在客户回复中说明缺少哪类价格依据。

### 8.7 续住咨询

```text
定位当前接待单
→ 查询当前订单
→ 查询目标续住日期库存
→ 调用 renew_candidates
→ 输出同房/换房候选与真实限制
```

只读阶段不提交 `renew`。

### 8.8 延迟退房

当前没有独立延退写接口。第一版评估：

```text
当前订单退房时间
+ 目标延退时间
+ 后续房态/库存
+ 门店延退政策
→ 可确认条件或仍需门店确认的部分
```

不能只查到原退房时间就停止，也不能说已经延退成功。

### 8.9 单个子查询失败

每个查询步骤独立记录：

```text
ok / empty / ambiguous / unavailable / unsupported
```

聚合规则：

- 成功事实继续回答。
- 只把失败影响的方面标为未确认。
- 只有完成当前 Task 所有必要事实都失败时，才给该 Task 的明确失败说明。
- 其他 Task 不受影响。

| 延迟退房办理 | 无已开放写动作 | 未实现 | 只做只读条件评估，不宣称办理成功 |

需要在实施阶段优先核对的字段：

- 当前有效订单响应中预订单与接待单的关联 ID。
- 房号字段是 `homeName` 还是其他字段，房型字段是 `roomName` 还是产品字段。
- 订单状态代码与中文状态字段。
- 库存的起止日期是否包含离店日。
- `available`、`sellable`、`sold` 的准确口径。
- `price`、`currency`、`consumeAmountType` 在真实响应中的位置。
- 续住候选的分页默认值和 `allowedHomeHandleTypes`。
- 会员权益中免费升房、折扣和有效期的正式字段表达。

写操作预留只使用文档已经存在的上下文字段：

- 酒店与订单：`hotelId`、`reserveOrderId`、`receptOrderId`、`orderStatus`。
- 房型与房间：`roomId`（房型 ID）、`homeId`（具体房间 ID）、`homeStatus`、`controlStatus`。
- 入住区间：`checkInTime`、`checkOutTime`。
- 续住已有正式字段：`renewType`、`renewPriceMode`、`renewHomeHandleType`、`startTime`、
  `endTime`、`newReserveOrderId`、`newReceptOrderId`、`reserveRemark`、`priceDetails`。
- 批量改价只沿用原文档已定义字段；它不等同于普通改房、排房、换房或延退接口。

改房型、排房、在住换房和延迟退房要真正开放，PMS 方仍必须分别提供：正式 endpoint 与 HTTP
method、完整请求 DTO、必填项/枚举、操作原因、幂等键、订单与房间版本号、并发冲突错误、成功
响应、失败语义，以及执行后用哪个查询接口和哪些字段确认结果。补齐前只保留内部契约，不注册工具。

## 10. 知识检索与 Judge 优化

### 10.1 修正可观测性

Retriever 日志在 Judge 前不能把所有未选择候选标记为 `context_limit_or_duplicate`。

建议记录四组 ID：

```text
rawCandidateIds
judgeCandidateIds
selectedCandidateIds
replyCandidateIds
```

淘汰原因必须具体：

- `below_score_threshold`
- `duplicate_same_source`
- `judge_candidate_budget`
- `judge_rejected`
- `selected_but_not_committed`

如果当时尚未经过 Judge，使用 `pending_judge`，不能写成已丢弃。

### 10.2 候选选择

继续使用现有 RawHits、门店层优先和总候选预算，不增加第二次检索或第二个 Judge。

需要保证：

- 与当前问题直接匹配的 FAQ 候选优先进入现有三个候选额度。
- 一个知识条目包含多组 FAQ 时，按当前问题展开成独立 FAQ 单元。
- 多问题各自保留候选额度，不能让前一题占满全局预算。
- 外卖地址、机器人存在、外部代点边界是不同事实，不能互相替代。

### 10.3 Judge 输入

Judge 输入保留：

- 当前客户原话。
- 自包含问题。
- 必要的上一条失败 Task 上下文。
- 完整候选问答。

不把派生的路由标签当成客户额外要求。

外卖场景的验收必须先查看真实候选全文：

- 如果知识明确写机器人可送上楼，直接回答该事实。
- 如果知识只写“有机器人”，只能确认有机器人，不能凭空承诺具体楼层、时间或已安排配送。
- 若门店业务期望固定回答“可以送到房间”，则应确认现有知识是否已经明确包含该事实；不通过本地硬编码补知识。

### 10.4 客户纠正

“啥玩意”“我问的是机器人能不能送上来”“不是这个意思”必须绑定紧邻的失败回复和原 Task：

```text
上一条 AI 回复失败或答非所问
→ 当前 relation=answer_rejected/correction
→ 复用上一 Task 的问题和证据范围
→ 只重新回答该 Task
```

只有存在多个同等可能的上一 Task 时才追问，不列出整段历史主题菜单。

## 11. 服务请求与人工路由

### 11.1 服务请求

| 客户表达 | 处理 |
| --- | --- |
| “毛巾在哪里拿” | 知识直接回答 |
| “送条毛巾来” | 先答知识；需要真实送物且知识无自助方案时，说明可记录服务请求，不自动转人工 |
| “空调不制冷，怎么处理” | 知识优先；无步骤时明确说明并询问是否创建维修工单 |
| “帮我建维修工单” | 进入现有 `create_ticket_with_confirmation` |
| “进度怎么样” | 查询现有工单进展，不重新建单 |

JEV 的 `maintenance/room_supplies/cleaning/lost_item` 保留业务分类；当 `objective=action_request` 且客户明确要求记录/报修/建单时，绑定现有工单 Graph Tool，不新增工单状态机。

### 11.2 人工路由

允许转人工的入口：

1. 当前客户明确要求人工、同事或人工客服。
2. 当前门店知识对该具体问题明确要求转人工。

优先级：

```text
PMS/知识可回答事实
→ 先回答
→ 再处理同一 Task 中知识明确要求的人工部分
```

禁止因为以下原因自动转人工：

- PMS 查询失败。
- 缺手机号、日期或目标房型。
- 普通升房、换房、差价、延退或续住咨询。
- 普通投诉、维修、用品、外卖、天气或闲聊。
- Generate 协议错误或空回复。
- Judge 证据不足但仍可追问关键字段。

同一消息重复回调必须保持现有幂等；成功话术继续由现有人工流程统一发送，Generate 不重复补发。

## 12. 回复组织规则

### 12.1 每个 Task 必须有结果

每个当前 Task 只能是：

- 已回答；
- 只追问一个必要字段；
- 清楚说明哪个方面暂未确认；
- 已进入真实资源、工单或人工流程。

不能无声遗漏，也不能用另一题的成功结果覆盖本题。

### 12.2 简短、像客服

- 普通单题 1 至 2 句。
- 多题按客户顺序，每题 1 个短段。
- 不重复客户已经说清楚的问题。
- 不先说“您是想问 X 吗”再回答明确问题。
- 不提供无依据的生活建议，例如客户说困了就建议调低空调。
- 不暴露接口名、Task、Judge、内部错误和测试环境。

### 12.3 PMS 只读边界

允许：

```text
当前查询到……
目前这个日期还有……
按当前会员权益……
根据现有价格，预计/精确差价是……
```

禁止：

```text
已经为您升房
已经锁房
已经换好
已经延迟退房
已经续住成功
```

## 13. 失败降级话术类型

不再统一使用“暂时没法准确回答”。

| 失败类型 | 客户可理解的回复方向 |
| --- | --- |
| 缺手机号 | “把预订手机号发我一下，我继续查这笔订单。” |
| 已有手机号 | 不追问，直接重新查询 |
| 多笔订单 | 给出日期/房型等最小区分信息，请客户选择 |
| 未查到有效订单 | 说明当前条件未查到，不断言客户没有预订 |
| 库存缺日期 | 只追问入住和离店日期 |
| 目标房型不唯一 | 列出 PMS 返回的真实房型，请客户选择 |
| 库存成功、会员失败 | 回答库存，说明会员减免暂未确认 |
| 会员成功、价格缺失 | 回答权益，说明最终差价缺少价格依据 |
| 知识部分回答 | 先回答已确认部分，不扩写未知内容 |
| 服务知识不足 | 说明没有可确认自助步骤，并提供真实工单选择 |
| PMS 暂时失败 | 说明本次实时信息暂未查到；不编造、不自动转人工 |

## 15. 实施步骤

### 阶段 A：建立可复现基线

1. 固定当前 release、代码 SHA、模型槽位和 PMS 配置。
2. 导出其风失败消息对应的 Intent、Task、工具调用、Judge Candidate ID 和最终回复。
3. 修正 Retriever/Judge trace 含义，先确认外卖答案真正在哪一步丢失。
4. 重新保存四份原始接口文档，只读归档，不修改内容。

### 阶段 B：手机号与订单复用

1. 实现当前 session 的 PMS locator resolver。
2. 当前新值与纠正值优先。
3. 复用最近成功查询条件。
4. 明确否定、切换订单和新 session 时失效。
5. 覆盖“就是上面那个”“那我几点退房”“换成大床房呢”。

### 阶段 C：确定性 PMS 查询计划

1. 为订单、库存、升房、换房、差价、续住、延退建立固定步骤表。
2. 每个操作定义机械必要参数。
3. 目标房型只使用 PMS 返回真实 ID。
4. 聚合每步结果，保留部分成功。
5. Generate 不再负责决定下一次 PMS 调用。

### 阶段 D：知识与纠错链路

1. 串起 RawHits、Judge Candidates、Selected 和 Reply。
2. 真实复现外卖机器人问题。
3. 只修发现的真实边界，不扩大本地语义判断。
4. 让 answer_rejected/correction 绑定紧邻失败 Task。

### 阶段 E：服务请求与人工路由

1. 普通咨询知识优先。
2. 明确建单绑定现有工单 Graph Tool。
3. 人工只接受明确客户请求或知识库明确指令。
4. PMS 可回答事实优先，不被知识转人工抢占。

### 阶段 F：回复与发布

1. Task 级部分失败回复。
2. 去掉多余反问和重复段落。
3. 完成自动测试和隔离真实会话测试。
4. 通过后再部署 test-2。

## 16. 测试矩阵

### 16.1 上下文

- 首次查单缺手机号，只问一次。
- 提供手机号后成功查单。
- “那我几点退房”不再问手机号。
- “就是上面那个”复用最近成功定位。
- 客户说旧号码错了但没有新号码，旧号码失效并追问新号码。
- 客户提供新号码，后续只使用新号码。
- 新 session 不沿用旧 session 手机号。

### 16.2 PMS

- 订单查询返回房型、房号、日期、状态和金额中客户实际询问的字段。
- 日期库存请求必须携带正确日期。
- 升房只形成一个客户决策结果，不重复回复。
- 当前房型、客户目标和 PMS 目标房型不混淆。
- 会员无免费升房权益时如实回答。
- 会员查询失败不丢库存结果。
- 价格为空不说免费。
- 精确差价、预计差价、无法报价三种状态正确。
- 换房中接待单失败但库存成功时保留库存事实。
- 续住调用 `renew_candidates`。
- 延退同时使用订单、房态和知识政策。
- 全流程无 HPMS 写请求。

### 16.3 知识与基础问答

- 外卖机器人首问直接回答现有知识。
- 外卖纠正追问只重答机器人问题。
- 外卖地址和机器人问题分别回答。
- 拖鞋问题直接回答，不先重复确认。
- 停车、WiFi、发票、周边、入住小程序继续正常。
- 普通聊天和通用知识正常。
- 天气真实调用天气工具。
- 多问题按原顺序全部回答。

### 16.4 服务与人工

- 空调维修咨询不自动转人工。
- 明确建维修工单进入现有确认流程。
- 普通用品请求不自动转人工。
- 客户明确要求人工只转一次。
- 知识库明确转人工正常执行。
- PMS 查询失败不触发人工。

### 16.5 客户自然问法验收

真实测试问题不写接口名称，至少覆盖：

1. “我今晚到店，帮我看看订单是不是已经生效了？”
2. “那我最晚几点退房？”
3. “这个房间有点小，能换个大床房吗？大概要补多少？”
4. “我是你们会员，换好一点的房型能免差价吗？”
5. “房间有点吵，今晚还有别的房能换吗？”
6. “行程改了，我想多住一晚，同房型还有房吗？”
7. “外卖到了，机器人能送到房间吗？”
8. “我问的是机器人能不能送上来。”
9. “空调不制冷，我住 1401，先告诉我怎么办。”
10. “帮我看今晚订单，再告诉我停车从哪里进。”

## 17. 验收标准

### 上下文

- 同一 session 和同一订单主题内，已提供手机号不会被重复索要。
- 客户更换、否定或取消后旧值立即失效。
- 旧手机号不会泄漏到非 PMS 回复。

### PMS

- 每个 PMS 客户目标都有固定的查询计划。
- 所有查询使用真实参数和真实返回字段。
- 指定日期库存不再使用默认当天。
- 升房、换房、续住、延退都能给出只读评估结果或明确缺失项。
- 子查询失败不抹掉其他真实成功结果。
- 不产生任何写请求和虚假办理承诺。

### 知识

- 已召回的直接 FAQ 能在 trace 中看到进入 Judge、被选中并进入回复。
- 外卖机器人问题不再因不可解释的候选丢失而通用失败。
- Judge 不裁决 PMS 事实。

### 客服体验

- 不重复确认明确问题。
- 不答非所问。
- 不无声漏题。
- 不把所有失败都说成“暂时没法准确回答”。
- 非明确人工或知识明确转接，不自动转人工。

### 可观测性

- 任一失败可明确定位在 Intent、上下文、查询计划、接口、Judge、Generate、Commit 或 Outbox。
- Retriever 日志不再把“尚未 Judge”误写成“因上下文限制丢弃”。

## 18. 发布与回滚

1. 只在独立 PMS 工作树实施。
2. 保留当前 release 和“薇薇2”备份不动。
3. 自动测试通过后，先在隔离会话执行上述 10 个客户自然问题。
4. 再用其风验证手机号连续追问、升房、外卖和纠正四个场景。
5. PMS 保持 `allowWrite=false`。
6. 验收记录分别标记：Intent、工具调用、事实正确、回复正确、真实投递。
7. 任一核心场景退化时回切当前 release，不恢复数据库，不删除新消息。

## 19. 明确禁止

- 禁止为“外卖机器人”写客户原话关键词硬编码。
- 禁止增加第二个 Intent/Judge/Agent。
- 禁止增加通用本地语义裁决器。
- 禁止增加“已答题目”持久化状态。
- 禁止把 Generate 继续当作 PMS 工作流编排器。
- 禁止因 PMS 或模型失败直接自动转人工。
- 禁止在没有真实接口字段时猜渠道单查询、房间属性或写操作。
- 禁止用今天空房推断整个入住期可分配。
- 禁止为了通过测试修改知识答案或固定测试回复。

## 20. 结论

当前系统不是“PMS 全部没接通”，也不是“模型完全不会理解”。订单、会员、当前房态等接口和基础客服能力已经真实通过。主要问题是：

```text
Intent 已识别客户目标
但已确认上下文没有稳定复用
且 PMS 多步查询仍由 Generate 自由编排
再叠加知识候选可观测性不足和全局失败兜底
最终造成重复追问、漏调用、部分成功被抹掉、答非所问和错误转人工
```

根治方向不是继续加判断门，而是收紧现有阶段职责：

```text
JEV 识别客户目标
Executor 按目标执行确定性只读查询计划
PMS Adapter 返回真实字段
Judge 只裁决知识
Generate 只组织已确认事实
```

这样既能系统性修复手机号、升房、换房、差价、续住、延退和外卖问题，也不会为了一个场景继续扩大链路复杂度。

## 21. 2026-09-22 实施结果

本方案已经按现有回复链路完成实现，未新增 Judge、Agent、数据库状态机或本地中文语义裁决层。

### 21.1 已完成能力

- PMS 查询参数改为按 action 白名单校验；订单详情必须使用真实订单 ID，库存必须具备有效入住/离店日期，手机号统一规范化。
- JEV 继续负责拆题；升房、换房、差价、续住和延退的相关维度保持为一个客户决策 Task，不在本地重新合题。
- Executor 在 Judge 后、Generate 前执行确定性只读计划，覆盖订单、库存、实时房态、会员、权益、升房、换房、差价、续住候选和延退条件。
- 同一会话可复用已确认手机号和订单定位；当前纠正、否定和取消优先，旧定位不会被静默恢复。
- 日期按客户原文顺序解析，支持完整日期、月日、日号、今晚、明晚和后天；“续住到某日”作为目标离店日处理，日期纠正只保留新值。
- 目标房型只接受客户明确要换到或升级到的房型，不把当前房型或整句客户原话当成目标房型。
- 库存按每个房型逐日校验完整入住区间，不把不同房型的零散日期拼成全程可售。
- 具体房号按实时房态每个房卡的预订/在住区间检查完整入住期冲突，排除锁房和维修房；结果只读，
  覆盖超出约 30 天或订单时间不完整时不确认。
- 差价直接使用同轮已查询的订单和库存快照计算，不再二次调用订单和库存接口；同轮相同查询使用运行级缓存。
- 订单客户事实同时读取根订单、`receptOrderList` 和 `reserveProductList` 中的客户侧白名单字段。
- 混合知识/PMS Task 中，PMS 事实不能代替知识证据；知识不足只约束知识部分，已确认 PMS 事实继续回答。
- PMS 优先级按 Task 生效：同一个实时问题的知识“转人工”不能抢占 PMS；独立兄弟 Task 的明确知识转接仍正常保留。
- 同 Task 的知识转接在 PMS 查询前只做延迟，不销毁 Judge 事实、候选或答案；PMS 有可用事实时取消该 Task 转接，缺参数、空结果或查询失败时恢复知识库原有 `direct` / `answer_then_handoff` 行为。
- 订单只读查询同时接受有效手机号或 PMS 已返回的 `customerNo`；会员信息与权益查询仍只接受客户手机号，避免把会员编号误当手机号。
- 库存完整性要求请求区间内每一天都返回 `available`，最小可售数只按请求日期计算，区间外营业日数据不会污染结论。
- “不是 23 到 24，改成 25 到 27”一类纠正会从替换边界重新解析，完整保留纠正后的入住、离店日期。
- 同一查询计划内互不依赖的只读请求并发执行：预订单与接待单查询可并发，日期已明确的库存与会员查询可并发；订单绑定、日期绑定和差价计算仍等待依赖完成。同参数查询使用并发安全的单次快照缓存。
- PMS 执行后同步 Intent、ReplyPlan 和 ToolKnowledge trace；Generate 不再获得已经执行完的 `pms_query`。
- 普通知识不足、PMS 失败、投诉和服务咨询不自动转人工；仅客户明确要求人工或当前 Task 的知识明确要求转接时进入现有路由。
- 维修咨询优先知识回答；客户明确要求建维修工单时复用现有 `create_ticket_with_confirmation`。

### 21.2 只读和安全边界

- 只读 action allowlist 不包含 `renew`，续住只查询 `renew_candidates`。
- 全链路没有调用 `Client.Renew`，没有改房、排房、换房、延退、改价或订单写入。
- 渠道订单号查询、改房型、排房、在住换房和延迟退房仅有未注册的编译期 Adapter 契约，不存在
  猜测 URL 或请求字段的 HTTP 实现。
- PMS 原始响应先经过客户字段白名单投影；手机号、Token、证件、内部备注和接口原始错误不会进入客户回复。
- 库存只表示查询时事实，不代表锁房；会员等级不等于免费升房；价格缺失不解释为免费。
