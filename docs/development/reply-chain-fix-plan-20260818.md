## 1. 问题定性（三个独立故障，一个数据因素）

### 故障A：异常 FAQ 抢占正常问题的证据首选（知识文字丢失的根因）
- cc77ebd 只拦了"提升人工"，**没拦"进证据集"**
- "给我办个入住"检索：转接行 0.79 排第1、正确答案 0.83 排第2（mixedRecall 排序不看分数绝对值）
- Generate 首选证据是"转接"→ 回复跑偏（"具体要办哪间房"）
- **同题判断是缺失的一环**："办入住"问句与"另一间房办不了"FAQ 不同题，但现状无任何同题校验

### 故障B：确认应答消息被意图链二次处理（反复问的直接根因）
- "不要"同时走了两条路：确认服务（兜底判cancel ✓）+ 意图链（分成 hotel_info 任务 ✗）
- 意图契约 `tasks.minItems=1` 逼模型给纯应答词编任务；提示词零"确认应答"教学
- 取消只关 job 不关账本任务 → 重试 job 从账本捞起"不要"任务再跑
- "不要"查库命中"两点前不要打扰我→转接" → 新确认 → 死循环

### 故障C：15 分钟寿限超时强制转人工（2045 凭空冒出的根因）
- `aiReplyJobLifetime = 15 * time.Minute`；超时走 `dispatchHuman("AI 回复任务超过等待时限")` → 无条件转人工池
- job 931 因故障B 卡在重试；15 分钟一到，**客户早就说了不要，系统反而强制发起转人工**
- 该分支无"客户已明确取消"检查

### 数据因素：混合语义库
- 管家/停车券/退订类"转接"行是**业务正确指令**（该转）
- 但它们与正常问题共享高频词（入住/不要/安静），现状无同题校验就互相误配
- 本版方案**不改知识库数据**（第4点已按你指示搁置），全部靠链路侧同题判定解决

## 2. 修复设计（三刀对应三故障，均为代码改动）

### 刀A：同题门禁——"转接"行进入提升或证据集都必须同题（治故障A）

**位置**：`internal/ai/runtime/executor/task_knowledge.go` `buildRuntimeEvidenceBundle`

**规则**（在现有 cc77ebd 守卫外层包一个统一函数 `transferFAQAppliesToTask(task, faq) bool`）：

对"答案含转接"的 FAQ，仅当满足以下任一**同题条件**才允许（1）触发人工提升（2）进入该任务的生成证据集：

1. **实词覆盖**：任务 Query 归一化后（去停用词：的/吗/呢/我/你/在/有/怎么/如何/办/个），剩余实词（≥1个且总长≥2）全部出现在 FAQ 标题中
   - "管家在吗"→实词{管家} → FAQ"有管家吗"含"管家" ✓ 同题
   - "停车券怎么拿"→{停车券,拿} → FAQ"停车券" ✓
   - "给我办个入住"→{给我办个入住归一后=办,入住}…需保留"入住"→ FAQ"另一间房办不了入住"含"入住"——**单字词会误判，故实词取最长名词短语**：入住场景锚词表
2. **锚词表匹配**（兜底，处理中文无分词）：预置业务锚词对 `subIntent锚 → FAQ标题必须含同锚`：
   - 入住/checkin：{办理入住,办入住,怎么入住,入住流程,在哪办入住,入住怎么} ↔ FAQ标题需含"入住"**且不含**否定/异常词（办不了|无法|不能|另一间|两间|手机|删|退）
   - 管家：{管家} ↔ FAQ含"管家"
   - 停车：{停车,车位,停车券,停车费} ↔ FAQ含"停车"
   - 退订/同住人/投诉类：锚=异常词本身（办不了/退/删/两间/手机不能用），**只有 Query 含同样异常词才同题**
3. **Jaccard 兜底**：归一化 bigram Jaccard ≥ 0.22（复用既有 structuredQATopicMatch 阈值）

**不同题时的处理**（治A的关键）：
- 不提升（已有）
- **从该任务的证据集剔除该行**（新增）——让排第2的正确答案上位为首选
- 剔除后若无任何证据 → 按现有 no_context 路径走"资料没写明"（不会发生在这两个case，正确答案都在第2位）

**效果矩阵（全部要写成回归测试）**：

| Query | 检索Top1 | 判定 | 结果 |
|---|---|---|---|
| 给我办个入住 | 另一间房办不了→转接 | 不同题（锚"入住"但FAQ含"办不了/另一间"异常词） | 转接行剔出证据；"在哪办入住"上位 → 知识文字+小程序 |
| 管家在吗 | 有管家吗→转接 | 同题（锚"管家"） | 提升转人工确认 ✓ |
| 停车券怎么拿 | 停车券→转接 | 同题（锚"停车"） | 转人工确认 ✓ |
| 我有两间房另一间办不了入住 | 另一间房办不了→转接 | 同题（Query含"另一间/办不了"） | 转人工确认 ✓ |
| 不要（纯功能词，见刀B） | 两点前不要打扰→转接 | 不进入检索 | — |

### 刀B：确认应答独占三件套（治故障B）

**B1 意图层教学+适配**（`intent_model_detector.go`）：
- 提示词新增：
  > 【转人工确认应答·独占】若紧邻上一条AI消息是转人工确认问题（含"请回复确认或取消"字样），当前消息若是确认/取消类应答（确认/取消/不要/不用/不用了/不需要/行/好的/嗯/OK/转吧/要），只输出一个 interaction 任务，requestMode=confirm_previous 或 cancel_previous，dialogueAct=confirmation 或 cancellation；禁止输出 hotel_info/hotel_variable/service_request/human_complaint_risk，禁止查询语义。
- 适配层归一化：`requestMode ∈ {confirm_previous, cancel_previous}` 的任务 → 强制 `intent=interaction, subIntent=confirm_answer|cancel_answer`，清 NeedsKnowledge/NeedsResource/NeedsHumanRoute（**这是硬保证，模型不守约也没用**）

**B2 纯功能词检索黑名单**（`task_knowledge.go`，检索前）：
- 黑名单：{确认,取消,不要,不用,不用了,不需要,好的,行,嗯,ok,要,转吧}（≤4字精确匹配）
- 命中 → **跳过知识检索**（不产生Query、不写检索日志）、knowledge_status=none、该任务直接由确认服务语义处理
- 这从根上杜绝"不要"撞上任何库内容

**B3 取消闭合补洞**（`conversation_handoff_confirmation_service.go`）：
- 判定 cancel 后，现有 `CancelHandoffTransactionDB` 基础上，**同事务**把该轮所有 `source_message_id=当前确认应答消息` 且非终态的任务置 superseded（reason=`consumed_by_handoff_confirmation`）
- 现有 `SkipPendingForMessage` 保留，但改为**终态 skipped**（非仅跳过），防 stale 恢复路径复活

**测试**：挂起确认 + "不要" → 断言：零新增 hotel_info 任务、零检索日志、仅一条取消回复；之后重试 job 恢复账本 → 无可跑任务 → job 正常收口。

### 刀C：超时转人工前检查客户意愿（治故障C）

**位置**：`internal/services/ai_reply_job_service.go` 超时分支（line ~560）

**改动**：`dispatchHuman(state, job, "AI 回复任务超过等待时限")` 之前增加检查：

```go
// 客户在本 job 生命周期内已明确取消过人工，超时兜底不得再次发起转人工
if route := ConversationRouteService.GetByConversationID(job.ConversationID); route != nil {
    if recentCancel := 已取消标记(见下); recentCancel {
        return AIReplyExecutionResult{Status: Completed, ReasonCode: "expired_after_handoff_cancel"}, errAIReplyJobExpired
    }
}
```

**已取消标记的实现**（不新增表）：在确认服务判 cancel 成功后，往 `t_conversation_event_log` 写一条 `event_type=handoff_cancelled`（含 message_id、时间）；超时分支查该会话**最近一条**该事件，若晚于 job.StartedAt 且其后没有新的客户消息 → 视为客户已拒绝，跳过 dispatchHuman，仅标记 expired。

**测试**：job 卡满 15 分钟 + 期间客户取消过 → 不发转人工、不发确认、job=expired_after_handoff_cancel；未取消过 → 维持原 dispatchHuman 行为（该兜底对真故障仍有价值）。
