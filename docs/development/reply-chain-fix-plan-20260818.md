## 2. 修复方案（四刀，按优先级）

### 第 1 刀：主题匹配门禁——"转接"提升与证据注入都要求同题（治 P1+P2，最核心）

**位置**：`internal/ai/runtime/executor/task_knowledge.go`（证据构建处）

**规则**：一条"转接"FAQ 要对任务 T 生效（提升人工 **或** 进入生成证据集），必须满足同题匹配，三选一即可：
1. 归一化后 FAQ 标题与任务 Query 的 bigram Jaccard ≥ 0.22（沿用既有 structuredQATopicMatch 的阈值）
2. 任务 Query 的全部实义词（≥2 字）都出现在 FAQ 标题里（"管家在吗"→"有管家吗"："管家"命中）
3. FAQ 标题与 Query 共享同一个业务 subIntent 锚词（入住/退房/停车/发票/管家/洗衣 等词典）

**同题匹配失败时**：该"转接"行**同时**从提升候选和生成证据集里剔除（这就是治 P1 的关键——不只是不转人工，还不能让它当证据）。

**效果矩阵**：

| Query | Top FAQ | 同题？ | 行为 |
|---|---|---|---|
| 给我办个入住 | 另一间房办不了入住→转接 | ✗（办入住 vs 办不了+另一间房） | 不提升、不入证据；"在哪办入住"上位为首选证据 → 知识文字+小程序 |
| 管家在吗 | 有管家吗→转接 | ✓（规则 2） | 提升转人工确认 ✓ |
| 停车券怎么拿 | 停车券→转接 | ✓ | 转人工确认 ✓ |
| 有没有安静房间 | 靠近电梯噪音→（无转接） | 不适用 | 正常知识回答 |

**测试**：上面矩阵四行各一条回归测试，另加"两间房办不了入住（真异常）→仍提升"。

### 第 2 刀：确认应答独占——存在挂起确认时，确认/取消词不进意图、不落知识任务（治 P3）

**位置 A**：`internal/ai/runtime/executor/intent_model_detector.go`（意图指令 + 契约适配）

- 意图提示词新增一条规则：
  > 【转人工确认应答·独占】若紧邻的上一条 AI 消息是转人工确认问题（"要我帮您转人工吗？请回复确认或取消"），客户当前消息是确认/取消/不要/不用/行/好的等应答时：dialogueAct 输出 confirmation 或 cancellation，任务输出单个 interaction 任务，requestMode 用 confirm_previous 或 cancel_previous，禁止输出 hotel_info/hotel_variable/service_request/human_complaint_risk 任务，禁止知识检索语义。
- 适配层（adapt 后的归一化）：requestMode 为 confirm_previous/cancel_previous 的任务，运行时强制 intent=interaction、subIntent=confirm_answer/cancel_answer、清掉 NeedsKnowledge/NeedsResource/NeedsHumanRoute

**位置 B**：`internal/services/conversation_handoff_confirmation_service.go`（取消闭合补洞）

- HandleCustomerMessage 消费确认/取消后，除现有 CancelHandoffTransactionDB 外，**同事务**把该轮所有 source_message 属于确认应答的任务（含尚未被本服务关掉的）置 superseded（reason=consumed_by_handoff_confirmation），确保重试 job 从账本恢复时捞不到"不要"任务
- SkipPendingForMessage 从"跳过该消息的 pending job"升级为"该消息进入终态 skipped（consumed_by_handoff_confirmation）"，防止 stale 恢复路径复活它

**位置 C**（兜底）：`task_knowledge.go` 检索前过滤

- 纯功能词黑名单（不要/不用/取消/确认/好的/行/嗯/OK）：长度 ≤ 4 且命中黑名单的任务**跳过知识检索**，knowledge_status 置 none，不产生 Query（连查都不查，杜绝"不要"撞库）

**测试**：模拟挂起确认 + "不要"消息 → 无新增 hotel_info 任务、无检索日志、只有取消回复；重试 job 恢复账本 → 无可跑任务。

### 第 3 刀：确认分类器加固（治 P4）

**位置**：`conversation_handoff_confirmation_service.go`

- 分类 prompt 收紧：系统提示明确"只输出 {decision, confidence, reason} 的 JSON，第一字符必须是 {，禁止任何思考过程"（当前模型吐"我们需要回答用户。…"开头的散文）
- 解析加固：先做宽松提取（首个 { 到最后一个 }，与 reply_output 的 extractLooseJSONObject 同款）
- 网关超时治理：确认分类超时从当前值降到 1.5s；超时/解析失败时兜底关键词判定维持现状（已是 cancel/confirm 词表，够用）
- 兜底判 unknown（如"我要开车出去"）时：**不消费消息，但同时给意图链发一条信号**（在 route state 写 hint：pending_handoff_seen=1），意图指令据此把该消息优先按新主题处理（避免继承转人工语境）——此条若实现复杂，可先只做"unknown 不再触发新确认"（第 1/2 刀已保证）

**测试**：模拟模型返回思考文字 → 宽松提取后正确判 cancel；模拟超时 → 兜底 cancel；模拟"我要开车出去" → unknown → 不再产生新确认。

### 第 4 刀：知识库数据治理（治 P5，需你拍板，代码不动）

建议把"答案：转接"的行分三类处理（FastGPT 后台操作，立即生效）：

| 类别 | 例子 | 建议 |
|---|---|---|
| 业务正确转人工 | 管家在哪/停车券/隔壁吵沟通/快递到了 | **保留**，第 1 刀的同题匹配会让它们只在正确场景生效 |
| 异常流程记录 | 两间房办不了/手机不能用/退订 | **保留**（真异常时转接正确） |
| 语义危险行 | 两点前不要打扰我（纯"不要"就能撞上） | **改写答案**：转接 → "如需免打扰请回复确认，我们将为您转接管家"（或至少在标题里加"免打扰"锚词，降低裸"不要"的误配分）；第 2 刀 C 兜底后此类撞库已基本不可能，改写是双保险 |

另：高架/停车券 FAQ 目前只在高铁南站店库，若南七店也需要，后台复制一份（每家店信息不同，答案要按店改）。

## 4. 风险与回滚

- 全部改动落在既有分支 `codex/checkin-miniprogram-direct`，逐刀独立提交，可单独 revert
- 第 1 刀的同题词典（subIntent 锚词）若漏词会导致该转的不转——上线后第一周观察"应转未转"案例，词典可热改（常量→可先硬编码，出问题改词重发）
