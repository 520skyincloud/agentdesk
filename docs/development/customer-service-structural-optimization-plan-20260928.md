# 客服全类型问题与回复链路结构性优化方案

日期：2026-09-28。状态：已进入实施，核心代码与自动回归已完成，正在交叉审查及真实验收。
以下各项是交付要求，不代表全部通过；实际部署、验收与剩余问题见同日结构优化实施交接。

依据：当前真实代码、`docs/design/reply-runtime-engine.md`及
[18轮真实客户问答验收](customer-experience-verification-20260928.md)。
测试基线为test-2运行版本22e6149，不能把旧版本历史问题与当前版本实测混在一起。

## 一、目标不是“多会几个接口”，而是能把客户的问题处理到位

最终应表现为：

1. 理解客户当下想知道什么、解决什么，不要求客户知道酒店房型名、接口名或内部流程。
2. 客户说过的定位信息继续使用；客户补充、纠正、选择、拒绝或转移话题时，正确更新当前任务。
3. 查得到就直接回答，需要比较就比较，需要引导就给一个有用的下一步，不把后台资料倾倒给客户。
4. 有部分信息先回答已知部分；不能查到的部分讲清具体限制，不装作完成，也不整体回复失败。
5. 简单问题简洁，复杂问题答全；多问题合理分段，不硬压成两句，也不连续发相同模板。
6. 不因普通需求、接口异常或模型失败自动转人工；真正的人工请求、适用知识流程和既定安全例外仍能正确处理。
7. 用客户最终收到的文字和卡片验收，不用HTTP成功、工具ok或Validate passed替代验收。

本轮优化覆盖所有同类型问法，不恢复六类固定演示问答，不为18条测试原句定制匹配。
不更换JEV供应商，不新增独立Agent、平行客服状态机、PMS后台或发送链路。
继续只读HPMS；“可换、可续、可报价”不等于“已换、已续、已锁房”。

## 二、现有问题归为六类结构缺陷

| 缺陷类型 | 已有证据 | 需要改变的职责 |
| --- | --- | --- |
| 只分类业务，没有稳定保存具体所求 | 退房时间退化为入住和离店；会员权益问成历史订单 | Intent保存对象、所求方面和话语作用，下游不再重复猜意图 |
| 查询产物冒充最终回复 | 会员目录和历史订单固定拼接，Generate被跳过 | PMS提供事实，现有回复层组织客户语言 |
| 证据在裁剪时被错误否决 | 毛巾门店自取答案进入检索结果但未进入Judge | 检索只做召回、去重、排序和预算，业务可答性由Judge判断 |
| 知识、动作和话术耦合 | 两条同义转接知识触发协议错误；生成话术可反向请求转接 | 事实与知识流程指令分开，动作只能由授权来源触发 |
| 自然语言生成丢失事实边界 | 当晚说成明天；无面积资料说更宽敞；仅有地址却说可送房 | 同一目标的事实、适用范围和缺失项一起进入回复；保留关键值约束 |
| 验收与用户体验脱节 | 工具和校验通过，但漏答、冗余、循环、等待22秒 | 分开验收需求、事实、表达、引导、耗时、投递 |

不能只把所有答案交给模型自由改写：那会同时增加延迟和事实漂移。
也不能继续用本地词表替模型理解每一种说法：那会把同类问题越修越窄。

## 三、各类问题应怎样服务客户

下表是业务行为要求，不是固定问答模板。

| 类型 | 典型客户表达 | 应做的查询与判断 | 客户应得到的结果 |
| --- | --- | --- | --- |
| 酒店知识与自助服务 | 停哪、收费吗、咖啡在哪、WiFi怎么连 | 查当前门店对应知识，分清位置、费用、方法及限制 | 先答所问方面，补必要位置或步骤；不增加无关政策 |
| 外部代办与配送 | 帮我点外卖、能送上来吗 | 分清代下单、配送、自取三个方面，查询门店边界和可用方法 | 不能代下单则说明边界，同时给已有地址或配送方法；不知道送房不等于不能送房 |
| 当前订单和在住信息 | 我几点退、我订的什么房、住到哪天 | 优先复用本次已定位订单；缺定位才询问支持查询的资料 | 只答所问字段；订单已结束时准确说明，不把历史单当在住单 |
| 历史住宿和金额 | 上次什么时候住、那次花多少 | 查询历史，按客户范围定位；多笔时给日期和房型帮助选择 | 回答那一笔的日期或金额，不每次重复全部订单 |
| 入住区间库存与房间可用性 | 今晚有大床吗、这两天哪间能住 | 结合目标区间、房型库存、房态与已知订单占用计算 | 说清所询期间的可用性；当前空净、整个期间可用、已锁定不能混为一谈 |
| 换房与升房 | 想换舒服点、换沐阳、会员能升吗 | 定位住宿和目标，查询库存、房间、真实属性、价格及适用权益 | 已指定目标就查目标；要求推荐就给有依据的优先选项，不把全店名单丢回客户 |
| 续住 | 再住一晚、原房能不能留、住到周三 | 从真实离店日和客户要求得到新日期，查原房占用、同房型备选及逐日价 | 明确哪晚、原房是否可留、多少钱；原房不行但同房型有房时给替代方案 |
| 延迟退房 | 能晚到两点走吗、会员能几点退 | 分清门店通用规则、本人权益、当前订单约定和是否适用 | 明确可依据的时间及必要条件；不把历史实际离店时间当会员权利 |
| 会员目录、个人权益和等级升级 | 有哪些会员、我是什么卡、怎么升钻石 | 公开目录无需手机号；个人资格查询本人会员及有效状态 | 问等级只答等级，问权益答权益，问升级解释条件；会员升级与房间升房严格区分 |
| 房价、差价、退款和优惠 | 补多少、会退多少、会员能免吗 | 区分订单费用、逐日价、挂牌价、优惠和最终结算；程序做有依据的计算 | 直接给能确认的金额及其含义；不能结算就保留已知报价并说明具体缺口 |
| 用品、清洁、维修等现场服务 | 毛巾不够、空调坏了、房间没打扫 | 先使用适用门店知识，区分自助、确需执行、知识明确转接 | 有办法先告诉客户；需执行时给真实接续方式，不用“可以登记”冒充已经处理 |
| 投诉、服务补救和减免 | 热得睡不着、一直没解决、能补偿吗 | 接住具体问题，结合订单与已批准门店规则评估解决方案 | 先解决住宿问题，再解释可适用的补救；不机械道歉，不临时编造赔偿 |
| 资源与商品 | 办入住、发定位、枕头同款怎么买 | 从现有绑定资源发送对应小程序、定位或商品卡 | 文本与卡片一致；买枕头与送枕头、脏枕头分开；不强制购买 |
| 语音、图片、错字与指代 | 发图片后问这个多少钱、语音补房号、口语错字 | 沿用现有媒体理解和原话来源，结合当前主题；确有歧义才澄清 | 不把未识别内容当事实，不要求客户重发整段；短句承接刚才的对象 |
| 闲聊、感谢、天气与泛化问题 | 谢谢、帮我看看、今天冷吗、你没理解 | 结合最近仍有效主题；实时外部事实只用已接入且成功返回的来源 | 自然接话，不静默、不乱查PMS；未有天气来源不能编造实时天气 |
| 人工请求与安全风险 | 找人工、受伤、明确求助 | 按既定授权入口，保留房号追问、员工接管和幂等 | 合法转接实际成功后仅一次“帮您转接到同事了”；已人工会话不抢答 |

名称、手机号、房号、订单号不是等价查询能力。
不能为了“像真人”要求客户提供实际无法用于当前接口定位的姓名，或声称支持尚未接通的渠道订单号查询。

## 四、统一主链路与职责

```text
现有消息收敛
  → Intent：理解本轮目标、对象、方面与上下文关系
  → 现有Executor：按目标调用知识/PMS/资源服务
  → Knowledge Judge：一次裁决知识证据和适用流程指令
  → 现有ReplyPlan：归并事实、缺失项和允许的下一步
  → 现有Generate：形成面向客户的答案
  → 现有Validate：协议、引用、关键值和操作授权
  → Commit → Outbox
```

“归并事实”是现有ReplyPlan内部职责，不增加模型调用阶段。
PMS和知识互补，按字段来源选用，不采用“PMS全局覆盖知识”或“没FAQ就不能回答”的规则。

| 模块 | 唯一负责什么 | 不再负责什么 |
| --- | --- | --- |
| Intent | 业务对象、当前目标、所求方面、补充/选择/纠正/取消 | 不决定有没有库存、是否免费、实际转接成功 |
| PMS Adapter/业务计算 | 真实查询、响应归一、区间与金额计算、确定性 | 不编写长篇最终客服话术，不重新分类原话 |
| 知识检索 | 权限范围内召回、去重、排序、可控输入量 | 不用“能否独自答全”提前淘汰部分知识 |
| Judge | 知识是否适用、支持哪些方面、知识流程指令 | 不重判PMS结果，不接管所有客户语言生成 |
| ReplyPlan | 当前问题要回答哪些事实，还缺哪些信息，可给何种下一步 | 不保存另一套会话状态机，不强制展示所有查到字段 |
| Generate | 按需求取舍、自然表达、对比、建议、追问和分段 | 不重新分类业务，不计算价格，不授予动作权限 |
| Validate/执行授权 | 来源、结构、关键值、隐私、写开关、动作与消息防重 | 不凭词表重判所有业务语义，不因生成话术触发转人工 |
| Commit/Outbox | 有序、幂等提交文本与卡片，记录真实投递状态 | 不把业务失败包装成成功，不恢复旧业务含义 |

### 4.1 事实优先级是按问题方面，不是按系统高低

- 当前订单时间、状态、库存：使用最新的适用PMS事实。
- 会员等级权益：使用会员接口，不能用历史订单反推。
- 停车、自助领取、配送、房型说明：使用适用门店知识。
- 换房优惠与补救：同时使用订单、会员和正式政策。
- 卡片与定位：使用现有门店资源绑定，不由文本模型生成链接。
- 数据冲突：保留来源和适用范围；先回答无冲突部分，冲突部分不擅自挑一个说确定。

“会员权益允许13点”与“订单原定12点”不一定是相互错误，可能是权益尚未办理到订单。
必须解释二者的实际关系，不简单让某一来源覆盖另一来源。

## 五、目标与有界上下文

### 5.1 扩展既有Task，不另造状态机

复用`IntentTaskTraceData/ReplyTaskPlanTraceData`已有的：
`Objective、DialogueAct、RelationToPrevious、Entities、SourceRefs、SupportedFacts、MissingAspects`。

仅在表达不足处兼容增加内部字段：
- 对象范围：公开政策、公开会员等级、本人会员、当前住宿、已选历史订单、候选房型。
- 所求方面：退房时间、名称列表、升级条件、费用、差价、可用性、推荐等，可组合。
- 当前选择引用及更新来源：客户选择还是客服建议，来自哪条已发送候选或当前原话。

具体命名在契约步骤确定；不新增消息表、会话表或客户对外接口。
旧审计无新增字段时不能据此猜当前选择；必要时由当前Intent重新理解，不回退整表直发。
JEV仍使用已接入的typed choice/noul方式，在已有Intent批次内完成；替换冗余问题，避免堆几十个字段导致批次膨胀。

### 5.2 一项业务决定是一个目标的多个方面

“沐阳有房吗，要补多少，会员能不能免”属于同一次换房决定，共享订单、日期、房型和会员对象。
不拆成互相丢失条件的三个独立业务流程。
“能换房吗，另外停车免费吗”则是两个独立目标，分别完成后按顺序答复。

### 5.3 客户说话方式的统一处理

| 对话变化 | 上下文行为 |
| --- | --- |
| 补手机号、“帮我查查” | 承接刚才未完成的问题，补定位后执行，不重新问查什么 |
| “那几点走”“一共多少钱” | 保留业务对象，替换本轮所求方面，不重复旧答案 |
| “随便、你推荐吧” | 按已知偏好及真实候选给一个建议，不当作语义无法理解 |
| “就这个、看看沐阳” | 绑定已查目录或已展示候选的真实标识，记录为客户选择 |
| 改号码、改日期、改房型 | 新值覆盖对应范围旧值，使依赖旧值的查询结论和报价失效 |
| 会员号码和预订号码不同 | 分别绑定对应业务对象，不悄悄把另一个对象也改掉 |
| “不是这个、我问的是……” | 纠正当前目标，不只道歉，也不再次输出原模板 |
| “先不换了、取消” | 终止旧办理目标；保留聊天审计，旧“好的”不得复活任务 |
| 新问题或闲聊 | 不继续推销旧房型；可保留定位资料，但不能自动沿用旧问题 |
| 隔天、订单结束、门店改变 | 稳定定位可在权限范围内保留；住宿、库存、价格、资格重新确认 |
| 多号码、多笔订单 | 不选第一条；只问能排除歧义的一项，提供客户看得懂的日期/房型 |

只保留当前有效业务快照、待补信息、已发送候选及近期必要原话。
引用失败的模型说法、未发送草稿或未核实建议，不能变成“已确认事实”。
同一轮有多个目标时保留对应Task引用；含糊追问没有唯一对象时才澄清。

日期以门店业务时区和PMS日期字段为准，不能使用开发电脑或客户设备时区代替酒店“今天”。
金额保留原精度，程序计算；手机号是查询定位信息，不因此标记为已核验。

## 六、PMS事实和业务处理

### 6.1 查到多少，不等于给客户看多少

PMS保留完整查询结果用于内部业务，但给回复层的只是：
- 本轮要回答的事实。
- 判断这些事实所必需的关联信息。
- 未确认方面及确切原因。

关键金额、时间、资格和状态复用已有结构化数据，补足来源、适用对象/区间、查询时间与确定性。
普通知识不做多层JSON包装。内部ID、证件、后台备注、Token和原始错误不进入客户答案。

例如问历史订单金额，模型需要的是“已选住宿、金额376元、金额字段含义”，
不需要把全店订单、会员升级条件和房态一起读一遍。

### 6.2 当前订单、历史订单和会员互不替代

- 当前订单为空时，可查历史帮助定位，但不能拿历史单当作当前住宿。
- 客户只问会员权益，不因为提供手机号就走订单查询。
- 多订单只追问一次必要区分；客户作出选择后后续问题沿用该单。
- “会员不存在”只说明该查询号码未匹配会员；已有号码不反复问，只有确需另一个会员绑定号码才问。
- 公共等级目录不顺带查个人会员，避免无关请求、隐私和旧号码污染。

### 6.3 换房、升房、续住与延退

流程收敛为：

```text
定位当前住宿
→ 确定客户目标和适用区间
→ 查询真实候选/占用/价格/所需权益或政策
→ 形成“可选什么、为什么、价格是什么”的只读方案
→ 客户追问或选择时更新同一目标
```

- 当前已指定房型就绑定该房型，不继续全店撒查；目标不存在与目标满房分别说明。
- 没有指定且要求推荐，通常提供一个首选和一个必要备选；依据真实价格、设施和偏好。
- “更贵、高楼层”不能推导为“更宽敞、更安静”；知识没有属性就不声称有。
- 目标无房，说明该区间确无库存后给有依据的替代，不只反问“那您选哪个”。
- 续住从已定位离店日推导，原房和同房型分别判断；已知日期不反复索要。
- 区间可用性复用`AssessStayRoomAvailability`。当前房态接口覆盖范围、占用记录完整度及30天边界必须保留，数据不完整不能推断无冲突。
- 尚未清洁、已锁、维修与未来可用分别处理，不把“全程无订单冲突”直接说成“现在可以入住”。
- 只读阶段客户“好的、就这间”只表示选定咨询方案，不触发HPMS写入，不要求客户确认一个实际无法办理的动作。

### 6.4 费用问题三种清晰出口

| 事实情况 | 回复方式 | 业务验收 |
| --- | --- | --- |
| 同区间、同币种、同套餐/计价口径及适用规则完整 | 复用精确计算，明确应补/应退及对应晚数 | 可以标精确报价完成 |
| 有当日或逐日挂牌价，但未完成订单结算试算 | 先给日期和挂牌价，再说明最终补退尚不能确定的具体原因 | 价格查询完成，补退需求未完成 |
| 缺日期、目标或必要金额 | 只追问真正阻断计算的信息，保留已知事实 | 未完成，不能用空值作零 |

复用`AssessPriceDifference`，不让模型心算，不把“新价减旧订单总额”当差价。
原单日期与新入住日期不一致时，不能把不同晚的两个数字机械相减。
会员折扣、免费升房、权益使用次数、订单渠道限制是不同条件，未返回的适用条件不能由等级名推断。

### 6.5 补救与30元规则

若沿用此前已确认的“同一次入住累计最多30元”方案：
- 必须绑定门店、同次住宿和已批准适用情形，不是每晚或每条消息30元。
- 先核对会员权益，再计算补救，不重复减免。
- 推荐/报价、已批准承诺、真实执行必须分开；单纯重复问价不能消耗或叠加额度。
- 复用`ServiceRecoveryCase`保存方案及幂等依据，并补齐同次入住累计核算与并发语义。
- 当前`ServiceRecoveryService`仅能记录申请，不能宣称现成的30元累计额度控制已经完成。
- 没有正式政策或问题责任尚未确定时先给可核实的处理方案，不按模型估计利润随意议价。
- HPMS写入、发券、退款仍关闭，不把建议或内部申请说成已减免、已到账。

## 七、知识检索、Judge与人工路由

### 7.1 减少本地语义判断，而不是再加一个检测门

检索侧保留门店/权限过滤、候选去重、相关性排序、输入预算。
退出裁剪阶段的“这个答案能否独自答全”“能否两条拼成完整答案”“是否应当转人工”等业务裁决。

预算以实际输入量为约束，先去重复问题和元数据，不再机械限制单题只留3条。
相关门店局部答案、明确转接条目和同题冲突证据必须可见。
不是把所有候选无限送给模型，也不新增一个筛选模型。

Judge仍只做一次知识裁决，输出：
- 可回答的事实及对应需求方面。
- 尚缺的方面。
- 适用的知识流程指令及来源、条件。

转接指令从`direct_single/direct_combined`的条数约束中分离。
多条同义转接来源可以支持同一个指令；实际互相矛盾的流程仍需按适用门店和条件区分，
不能简单放宽协议后把所有“转接”合并执行。

事实、局部答案和服务指令可以并存：先答已知部分，再处理确需人工的部分。
Judge后不再由多组本地精确FAQ、转接补救函数反复改写同一个业务决定。

### 7.2 人工只有一个授权出口

允许来源仍为：
1. 客户明确要求人工，或接受与当前问题绑定的有效人工邀请。
2. 当前门店/适用知识明确要求该问题进入人工流程。
3. 已约定的严重安全风险例外。

普通问题缺知识、PMS暂时失败、解析失败、价格不足、模型写了“转接”，都不是授权。
移除“生成文本出现人工承诺，所以再触发真实转接”的反向入口。
生成文本错误应在原回复流程纠正，不能赋予操作权限。

- PMS能回答的当前方面优先答，但不能用无关订单事实压掉确实需要现场处理的问题。
- 有自取信息先保留自取信息；知识明确规定送房要转接时，再处理送房这一方面。
- 客户拒绝人工时，普通流程不自动转；安全风险按已确认例外处理，不能由模型随意扩大。
- 继续复用现有房号追问、人工状态、员工接管、幂等和成功话术。
- 房号已明确且仍有效不重复问；确需房号的现场服务才追问，咨询类人工不强行要求房号。
- 用户说“你没回答我”不等于要求人工，应先重新解决当前问题。

### 7.3 维修和服务补救要有真实接续

空调问题应回应客户不适，然后走门店已有流程，不能把协议解析失败说成没有资料。
已命中转接知识就正确进入既有流程；能自助排除的按明确步骤回答。
只有工具真实建立工单才说已登记；若本轮不接通执行能力，则明确当前可做的下一步，不暗示已经派人。
客户持续反馈未解决时，保留该服务目标、已尝试步骤和未解决点，不重复开场或同一句建议。

## 八、回复层与提示词的统一修改

### 8.1 去掉PMS长模板直发

首版将PMS业务事实统一交现有Generate形成客户回复，退出会员目录、历史订单等固定长摘要直发。
不是仅删除一个函数：同时移除这些摘要作为`AnswerText`和“必须照读事实”的双重来源。
单题知识若已有Judge生成的完整自然答案，可以沿用现有直接提交，避免再次复述。
这里的完整指当前所求方面已覆盖、没有未决比较或上下文资格判断；复用现有Task/Judge结果选择出口，
不再添加一轮语义判断。PMS与知识混合问题统一由现有Generate组织，两种来源都不得丢失。
必要字段追问、资源发送成功控制话术仍复用，不新增另一套快速回复引擎。

此调整可能让原来1至2秒的模板答复增加一次现有Generate调用，必须实测。
通过少查无关数据、压缩输入及并行查询抵消，不能先保证速度不受影响。
暂不新增PMS“窄直答白名单门”；稳定后有性能证据再评估，不在本轮增加分支。

### 8.2 输出不是后台字段列表

默认组织顺序为：
**直接回答当前问题 → 必要依据或限制 → 一个能推进的下一步。**

- 简单问题一句足够；复杂比较、政策多条件允许短段，不强制8至28字或最多两句。
- 客户问全套权益时应完整整理，不能以“简洁”为由漏掉明确要求。
- AND/OR、日期、折扣解释成自然中文，不能因自然改写改变条件。
- “未查到会员”说明本次定位结果；“请求失败”说明暂时无法确认；不能统一说“没有”。
- 不说“没能整理成可靠回复，请再发一次”，系统保留原问题自行完成有界恢复。
- 不在每条答案结尾附加转人工、确认办理、推销或无意义的追问。
- 暖意来自回应具体处境和有效帮助，不靠“亲、感谢理解”等模板堆叠。

示例仅为验收方向，不作为固定匹配文本：
- 问有哪些会员：先说明普通、银卡、金卡、钻石四级，不主动粘贴全部保级条件。
- 问银卡能否享受刚说的钻石15点：直接说明当前银卡对应13点，不是15点。
- 问上次花多少：答对应订单金额，不重复入住时间。
- 报价资料不足：先说明所询日期目标房型价格，再说最终补退尚未核实的具体部分。

### 8.3 清理所有生效提示词来源

范围包括基础Assembler、数据库Agent规则、技能指令、动态场景提示、工具附录及失败恢复提示。
记录实际运行拼装来源和指纹，敏感配置不入报告，避免只改代码却被旧运行配置继续覆盖。

统一移除或改写：
- Generate再次识别五大意图的要求。
- “任何真实服务都不能查/只能人工”等过期泛化限制。
- “不能说帮您查、确认”等对现有只读能力的无差别禁止。
- 默认一两句和过短字数限制，与多问题完整回答相冲突的规则。
- 泛化的“查不到就人工”“生成失败就人工”和没有执行能力却承诺登记的兜底。

保留：不虚构、不越权、不假承诺、不泄露内部字段；从句式禁令改为动作结果和权限边界。

### 8.4 一次输出校验，保留必要安全

复用现有`replyParts/coveredFactIds/Validate`，不增加在线语义审核模型。
校验来源引用、关键日期和金额、订单/会员对象、授权动作及资源绑定。
日期和金额先由服务端格式化；相对日期如出现，按同一酒店时钟归一后核对，不能跨夜漂移。
只校验回复实际采用的事实，不要求客户看见全部查询结果。

逐步退出词组式“主体、能力、范围”的重复本地重判，用相关事实输入和现有证据契约约束表达。
这不等于能够数学保证所有自然语言永不犯错；未见问法和真实客户旅程仍是发布门槛。
发现生成漂移必须定位输入、事实范围或生成契约，不能再新增一串问题专用禁词。

### 8.5 分段与资源发送

- Task是独立业务目标，不等于必须只有一个气泡，也不等于每个字段一个气泡。
- 单问题先去冗余；多问题按客户顺序组织，通常控制在1至3条文本内。
- 同一目标的结论和必要条件可以同条换行；不得为了看似分段把长表分三次轰炸。
- 继续使用原Commit和稳定消息ID；文本、卡片、定位保持正确关联、顺序和防重。
- 枕头购买发枕头商品卡，入住发入住小程序；文字口令不作为卡片验收。

## 九、失败类型及对客户的处理

| 内部结果 | 应怎样继续 | 不能做什么 |
| --- | --- | --- |
| 缺必要定位 | 追问一个真正能推进查询的字段，保留原目标 | 重问已提供手机号，或问无接口支持的字段 |
| 查询无匹配 | 说明本次范围未匹配；必要时区分当前/历史或核对绑定号码 | 断言客户没有预订或接口不存在 |
| 多条匹配 | 用日期、房型等展示少量候选让客户选 | 擅自取第一条 |
| 认证、网络或业务服务失败 | 保留已知答案，具体说明该项暂不能确认 | 把失败说成无订单、无房或自动人工 |
| 知识/PMS部分成功 | 每个目标分别答、追问或说明限制 | 一项失败抹掉全轮内容 |
| Judge/Generate协议失败 | 有界恢复一次失败Task；保留已核实的其他结果 | 重跑整轮、无限重试、请客户反复重发 |
| 真正能力受限 | 给实际可做的范围，必要时询问是否需要同事协助 | 编接口、编结果、把建议当已办理 |
| 投递失败 | 由现有Outbox按幂等ID重试，单独标记送达状态 | 重做PMS业务或重复触发转接/发卡 |

如果生成协议整体不可解析，不能假装能定位到某个失败Task：
已合法生成或已提交的部分保留，只有可唯一归属的失败部分才单独恢复；
整体不可解析则在原整轮预算内恢复一次，不能对每个Task各重试一整轮。
恢复后仍失败，使用指向原问题的简短受限告知，不暴露协议术语、不要求重发已知资料，
不把技术失败说成没有订单或没有库存，并明确将本轮标为程序失败。
这是故障终态，不重新引入整单/会员长模板，也不能计为业务通过。

恢复必须受整轮时间预算约束；超时不继续后台生成过期消息覆盖客户新问题。
只有有效答案和已提交动作进入后续上下文，失败日志不能污染“已完成”状态。

## 十、速度与安全不靠砍掉正确答案来换

优先优化已有链路：
1. 订单、会员与知识查询在依赖允许时并行；先有订单再依赖日期的步骤保持正确顺序。
2. 复用现有同轮查询缓存，同一手机号、订单、日期和门店不重复查；公开目录不额外查个人信息。
3. Judge输入去重、减少冗余说明及候选元数据，保留直接相关事实，不再按固定3条截断。
4. 同会话静态知识追问可复用带来源版本的已确认事实；政策版本改变即失效。
5. 库存、价格、会员适用性在新的业务决策前重新查询，不用旧快照承诺实时可用。
6. 缓存键包括门店、权限范围、业务对象及日期，不跨客户共享个人资料。
7. 不把多个外部模型的超时和重试层层叠加；在现有预算内收口，不再新增检查模型。

首轮性能目标，不是已达成承诺：
- 简单知识、资源和已知信息追问：5秒以内。
- 普通PMS查询：8秒以内。
- 多题、推荐与多源评估：12秒以内。
- 超过20秒的轮次必须逐项定位，不用“正在查询”先发一条掩盖最终答案迟迟不来。

小规模验收逐条公布实际耗时；有足够稳定样本后再报告P50/P95，不用两次测试宣称长期SLA。
同时记录Intent、检索、Judge、PMS、Generate、Commit/Outbox耗时，不能只优化一个阶段。

隐私、跨门店、员工接管、HPMS只读开关和动作防重仍是必须保留的硬边界。
测试免核验不可默认为生产免核验；手机号查询成功不提升身份认证状态。

## 十一、实施步骤、文件与退出条件

不先全面删除旧代码再重建。每一步明确新职责接管哪些旧职责，测试通过后让旧逻辑退出实际调用。
不长期保留两套语义解释同时运行，不改无关后台、计费或前端。

| 阶段 | 主要工作及预计文件 | 该阶段完成标准 |
| --- | --- | --- |
| 0 基线与契约 | 现有18轮证据、有效提示词来源；callbacks内部Task/事实契约设计 | 明确各类型成功结果、已有能力和真实缺口，不改运行行为 |
| 1 目标与上下文 | `jev_intent_detector.go`、`intent_model_detector.go`、`intent_runlog_context.go`、`pms_read_planner.go` | 对象、方面、选择、纠正、取消一致；退出对应本地原话关键词再解释 |
| 2 知识与事实 | `answerability_gate.go`、`knowledge_evidence_judge.go`、`pms_read_execution.go`、`pms_read_catalog.go` | 正确知识不会先被删除；事实与转接指令分离；PMS不生成长模板客户答案 |
| 3 回复与授权 | `service.go`、`assembler.go`、`multi_reply_output.go`、`generated_reply_validator.go`、现有人工入口 | 去掉PMS业务默认直发及话术触发动作；自然回复保留事实范围，资源和人工幂等正常 |
| 4 分段与性能 | 现有上下文/查询复用/时间预算；必要时兼容调整`reply_commit_service.go`内部映射 | 多题完整、单题不冗余，相关真实旅程达到耗时目标；超标单列性能未通过，不能仅记录瓶颈便标完成 |
| 5 实收与发布 | test-2隔离真实链路、获准企微收件端、部署和回滚记录 | 业务验收、事实、语言、投递分别达标，不能用一个总通过率掩盖失败 |

第1至3阶段是同一个结构性改动的依赖步骤，允许分步提交和回滚，但不把半套契约发布给全环境。
30元补救若纳入交付，另在现有`ServiceRecoveryService/Case`内实现累计核算和必要repository事务，
必须独立通过重复与并发测试后才能宣称该规则可用，不阻塞基础问答修复。

影响范围：
- 优先只有内部Task/事实/回复契约兼容新增，不修改对外API、企微协议、消息表、WebSocket或Outbox契约。
- 暂不需要新表或DDL。若后续发现确需补救查询索引/字段，再单独提出兼容AutoMigrate，不静默扩大。
- 不改模型供应商、token计费口径；通过原调用路径记录实际新增/减少的模型调用。
- `answerability_gate.go`、`multi_reply_output.go`、`reply_commit_service.go`等与ai-billing有共享范围，实施前重新fetch、逐文件比较并确认契约及合并顺序。
- 独立PMS工作树开发，不触碰customer-audit脏工作树；不修改“薇薇/薇薇2”。

## 十二、验收必须证明客户真的受益

### 12.1 不再只有一个“通过”

每轮保存客户原话、实际调用对象、必要事实、真正发出的全部消息、耗时及投递证据。
分别记录：

1. **理解是否正确**：对象、方面、最新选择、日期没有错。
2. **事实是否正确**：每项结论有适用来源，未确认事项没有说成确定。
3. **需求是否完成**：问能否、几点、多少钱，是否得到直接结论；未完成的部分是否有有用下一步。
4. **表达是否合格**：无无关数据、无循环、无内部术语，多问题完整且分段适当。
5. **性能是否合格**：最终必要回复耗时，而非第一条占位消息时间。
6. **交付是否成立**：本地提交、渠道回执、收件端出现、卡片打开分别确认。

最终状态只能是：完整完成、正确部分回答但未完成、外部条件受限、程序失败、尚未验证。
正确拒绝编造差价可以是合格的受限处理，但不能被计为“精确差价功能完成”。

### 12.2 有限且覆盖类型的测试

- 将原18轮变为脱敏可重放回归，防止已发现问题复发；不把这些原句写进生产匹配规则。
- 原18轮证据回放固定原会话边界和当时时钟，不直接将9月28日订单、库存及日期预期套在日后的真实环境。
- 每次真实旅程前只读核对专用样本的订单状态、酒店业务日、库存、会员及价格依据，再按客户方式提问。
  样本已退房、无库存或权益变化要更换适用样本并记录，不能把自然业务变化误判为程序退化。
- 原房可续、目标无房、会员未匹配、价格依据不足至少各有对应真实样本；缺样本标未验证，
  不能用一次“未查到”宣称续住、换房或会员能力已通过。
- 自动测试覆盖：同义表达、顺序变化、对象和范围、跨时区/跨日、多晚金额、空价格、多订单、纠正号码、房型选择、取消、重复回调。
- 注入失败只在契约/测试环境：认证失败、超时、部分成功、知识冲突、Judge格式错误、Outbox失败与重试。
- 真实测试按短旅程进行：到店与知识、当前住宿与续住、换房推荐与差价、会员资格、历史订单追问、服务与资源。
- 每类型至少两个不同客户表达，其中至少一次是连续追问或混合问题；测试题包含未用于开发的新表达。
- 先执行6条短旅程，每条约4至5轮，分属隔离会话；按覆盖矩阵补足缺项，不做单窗口30/50轮无限循环。
- 涉及转人工的题在独立会话结束，不继续在已人工状态下评测AI；隔离范围还要阻断或限定门店通知接收者。
- 修复后只重测失败旅程和受影响的相邻类型，再跑发布关键集；同类失败再次出现先回查结构原因，不靠反复抽到成功样本。

各类型两个表达是最低覆盖要求，不是数学可靠性保证。覆盖不足就在报告标未验证，不凑通过率。

### 12.3 发布硬门槛

以下问题在已执行发布集出现任一项，不能扩大启用：
- 串客户/串门店、敏感数据泄露。
- 日期、价格、会员资格、房间属性或执行状态被虚构。
- 无授权转人工、未授权PMS写入、重复动作或卡片。
- 空回复、漏掉独立问题、持续追问已知字段、未使用最新纠正。

已知缺口不能被措辞美化后当成功；有明确外部限制的场景单独列为受限，不与程序错误混算。
性能验收独立生效：内容正确但超标只能标“内容通过、性能未通过”。
对照同类型修复前后耗时，新增Generate造成明显回退不能扩大启用。
外部服务瓶颈也不是完整交付的豁免理由，只能保留有限验证范围；达到整轮预算时必须终止过期回复。
PMS无写操作需同时核对实际调用操作和写开关，不能只看操作表行数为0。
隔离测试不等于企微实收；枕头卡、入住小程序、定位和分段文本都要在获准收件端验证。

## 十三、接口边界与交付清单

已经验证存在的能力继续使用，不重复向PMS方索要：
- 手机号当前/历史订单查询。
- 会员信息、等级目录和权益。
- 房价看板、库存、实时房态及现有范围内的占用计算。

最终变更报价、权益使用次数/适用状态及写操作等，必须逐项区分：
“没调用已有接口”“参数或对象错”“解析失败”“已返回但缺字段”“确未提供正式能力”。
只有核查后才能给开发方接口缺口表；本方案不声称重新整理回复即可自动获得所有最终结算和写入能力。

最终交付给用户：
1. 每类问题的实际问答及其第二种表达，不只给功能名称。
2. 修复前后对比、剩余问题、耗时和真实投递情况。
3. 已完整完成、仅查询可用、外部受限、尚未验证四类清单。
4. 当前release、发布范围、PMS写开关及回滚位置。

发布前备份当前程序、配置及必要数据库快照；先隔离，再获准实收，再扩大test-2启用。
异常只回退本轮程序/相关配置，保留聊天、审计和业务记录，不恢复旧数据库、不覆盖备份版本。
不以“不能出现任何新问题”作无依据承诺，而以类型覆盖、依赖回归、实收证据和可回滚发布控制风险。
