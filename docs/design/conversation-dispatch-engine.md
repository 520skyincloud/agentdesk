# 会话智能派单引擎

> 状态：当前实现依据（2026-07-16）
>
> 适用范围：客服组待接入会话的人工、规则和智能派单
> 代码优先：文档与代码冲突时，以 `conversation_dispatch_*`、`conversation_human_dispatch_service.go` 和 `message_service.go` 的真实调用链为准。

## 1. 目标与边界

派单引擎解决值班期间持续、不定时进入的人工会话分配问题。它需要同时保证：

- 只向当前值班且具备服务资格的客服派单。
- 当前任务、待首响、待回复、连续消息积压和本班累计工作量尽可能公平。
- 结合客户上下文、紧急程度、问题复杂度和历史接待连续性选择更合适的客服。
- 模型不可用、输出不合法或判断不可靠时，自动降级为确定性规则，不阻塞人工服务。
- 组长继续保留手动派发、转派和释放能力。

Conversation 仍是唯一派单单位，ConversationAssignment 记录每次分配快照。本实现不新增平行任务表，不改变 Conversation/RouteState 状态机，也不把工单并入即时会话派单。

已派发会话保持客服连续性。客户继续发消息时不会自动把会话抢走或反复转派；新的消息积压会进入该客服的实时负载，影响后续新任务的分配。

## 2. 客服组派单模式

`AgentTeam.DispatchMode` 支持：

| 模式 | 语义 |
| --- | --- |
| `manual` | 不参与系统自动派单，任务留在组长编排池 |
| `rule` | 只使用确定性候选约束和公平负载排序 |
| `intelligent` | 先执行全部规则约束，再由租户授权模型在合法候选中判断；失败时降级规则 |

历史客服组和未传派单方式的创建/更新请求默认使用 `rule`，避免升级后意外产生模型调用。模式在现有客服组编辑弹窗设置，复用 `agentTeam.update`，不新增隐藏权限或平行配置页。

## 3. 持续派单触发

系统通过即时触发和周期补偿共同处理持续流入的消息：

1. AI 转总部人工成功进入 `HQ_AGENTDESK_PENDING` 后，安排一次 800ms 防抖派单。
2. 待派发会话收到新的客户消息时，重置同一会话的 800ms 防抖计时，让模型读取较完整的本轮输入。
3. 会话被释放、进入客服组待派池或进入全局待派池时，安排防抖派单。
4. 客服状态、排班等既有变更入口继续触发待派任务重试。
5. 定时任务每 30 秒扫描一次待派会话，补偿进程重启、瞬时冲突和遗漏事件。

同一会话同一时刻只运行一次派单。新消息在模型判断期间到达时，事务内 `LastMessageID` 校验会拒绝旧判断，并重新安排派单。实时防抖调度只在服务器完成数据库和 cron 初始化后显式启用；定时器还会核对数据库实例和连接状态，避免测试或进程生命周期切换后的越界任务。

## 4. 待派队列

周期扫描默认每批最多处理 50 个会话：

- 单租户内按有效优先级、进入人工池时间和 ID 保持稳定顺序。
- 投诉、紧急、危险、退款、报警、无法入住、受伤等关键词提高规则优先级。
- 每等待 5 分钟增加 10 点优先级，等待加成最多 40 点。
- 多租户之间轮转取一条，避免单一租户的大批积压长期占满一轮扫描。

优先级只决定先处理哪条待派会话，不允许绕过客服资格、容量或租户边界。

## 5. 合法候选约束

模型调用前先构造合法候选池。客服必须同时满足：

- 与会话属于同一租户。
- 所属综合客服组启用，且派单模式不是 `manual`。
- 当前存在有效排班；指定客服小组值班时必须是该小组有效成员。
- User 和 AgentProfile 启用，自动接单开启，服务状态为空闲。
- 未超过 `MaxConcurrentCount`。
- 满足门店和企微员工号服务范围。
- 已知离线且不接收离线任务时不进入候选。

客服组解析沿用现有事实源顺序：会话当前组、企微员工号/门店员工绑定与客服组服务范围、接待策略的客服组配置。模型不能增加候选、跨租户选择或绕过排班。

## 6. 公平负载

每次派单都从数据库重新计算候选负载，不依赖页面缓存。核心指标包括：

- `activeCount`：当前处理中会话数。
- `weightedOpenLoad`：当前会话任务权重，加上连续未回复消息压力。
- `pendingFirstReply`：派发后尚无客服首响的会话数。
- `pendingReplyCount`：客户最新发言后仍待人工回复的会话数。
- `shiftAssignedWeight`：当前班次开始后累计派发的任务权重。
- `lastAssignedAt`：最近派单时间，用于同负载时轮转。

连续消息压力按会话动态计算：第二、第三条连续未回复客户消息各增加 1 点；最早未回复消息等待满 10 分钟增加 1 点，满 30 分钟再增加 1 点。该压力有上限，避免客户拆分短句无限放大任务。

综合负载公式为：

```text
(weightedOpenLoad + pendingFirstReply * 0.75 + pendingReplyCount * 0.5)
/ max(MaxConcurrentCount, 1)
+ shiftAssignedWeight * 0.03
```

规则候选按综合负载、本班累计权重、当前会话数、最近派单时间和既有客服优先级稳定排序。这样既防止一名客服当前过忙，也防止短时间内持续把新任务派给同一人。

## 7. 模型判断

仅智能模式使用模型。模型配置通过租户统一模型解析器读取用途 `dispatch_decision_llm`，遵守平台授权和租户默认模型边界；租户不能看到平台密钥。

模型不是每次派单都调用。系统先以最低综合负载客服为基准建立公平候选带：综合负载差不超过 0.20，且当前加权负载差不超过 1。只有公平带内至少存在两名智能模式客服时才调用模型；只有一名合法客服、负载差距已经明显、客服组为人工或规则模式时直接按规则派发。这样模型只在公平结果接近时比较客户连续性和问题适配，避免无意义调用，也不能为了语义偏好扩大工作量差距。

模型只接收规则层筛出的前三名候选，以及：

- 会话、客户、转人工原因和等待时间。
- 最近 12 条客户、AI 和人工客服消息，每条内容限制长度。
- 候选客服实时负载、容量和本班累计权重。
- 候选客服是否处理过该客户。

任务评分使用固定口径，避免不同批次随意放大工作量：权重 1 表示标准问答或单次确认，2 表示一次人工核实，3 表示多步骤处理或单部门协调，4 表示投诉、技术故障或跨部门协调，5 仅用于安全/健康/财产风险或长期复杂跟进。优先级 0-39 为普通事项，40-69 为明确时限或催促，70-89 为严重投诉、服务中断或紧急故障，90-100 仅用于人身安全、健康、治安和重大财产风险；客户自行提出较短期望时间不直接等于高风险事件。派单理由必须引用真实负载、待首响、历史连续性或问题特征，禁止用随机或用户编号作为选择依据。

客户消息和转人工原因被明确标记为不可信资料，不能作为模型指令。模型只能返回以下严格 JSON：

```json
{
  "selectedUserId": 101,
  "workloadWeight": 3,
  "priority": 70,
  "confidence": 86,
  "reason": "负载较低且处理过该客户"
}
```

约束如下：

- `selectedUserId` 必须属于候选列表。
- `workloadWeight` 为 1-5。
- `priority` 和 `confidence` 为 0-100。
- 不允许额外字段、额外文本或 Markdown。
- 单次调用超时 8 秒；格式错误允许重试一次。
- 置信度低于 60、模型不可用、超时、输出不合法时降级规则。

进入模型的候选已经受公平带限制；提交前仍按同一阈值执行公平保护复核。模型负责语义判断，不拥有最终权限。

## 8. 事务与并发

最终写入在 service 事务中完成，并锁定会话、客服档案和客服组。提交前重新检查：

- 会话仍待接入、未分配、租户一致且最后消息未变化。
- 客服账号/档案仍启用、可自动接单且服务状态可用。
- 客服组模式仍允许自动派单。
- 排班、小组成员、门店/企微服务范围仍有效。
- 最大并发仍有容量。
- 当前处理中、加权负载、待首响、待回复、本班累计权重和最近派单时间仍与候选快照一致。

校验成功后，同一事务写入 Assignment、Conversation 的客服/客服组/状态/优先级/权重、事件日志，并把 RouteState 更新为总部客服处理中。任一写入失败都会整体回滚，事务提交后才发布既有 WebSocket 会话变更和 ConversationAssignedEvent，避免出现“会话已分配但路由仍待接入”或相反的部分状态。

总部客服正式接单时，人工服务超时窗口从派单成功时间重新起算；不能沿用客户进入待派池前的最后消息时间。接单后的客户新消息与客服回复继续按既有规则刷新人工空闲窗口，避免客服刚接单就因客户此前等待时间被误判超时。

Assignment 保存派单方式、模型置信度、任务权重、理由和小组快照。组长手动派发/转派记录为 `manual`，规则派单记录为 `rule`，有效模型选择记录为 `intelligent`。

## 9. 页面与权限

不新增页面：

- 客服组编辑弹窗增加人工、规则、智能三段式选择。
- 现有派单工作台展示任务权重、优先级、派单方式、置信度和理由。
- 现有客服负载区展示当前加权负载、本班累计权重和综合负载。
- 会话工作台继续负责客服实际回复，派单页不重复聊天能力。

权限继续使用现有全局权限派发制：客服组模式修改使用 `agentTeam.update`；派单列表和负载使用 `conversation.view`；人工派发、转派、释放和手动自动派发使用 `conversation.handover`。本实现没有内部隐藏权限。

## 10. 模型用量与计费边界

每次真实模型调用写入既有 `AIUsageEvent`，`stage` 和 `operationType` 均为 `dispatch_decision`，记录租户、会话、消息、模型来源、token、耗时和调用结果。格式重试作为独立调用证据记录。

本实现只增加派单用途和真实调用证据，不修改价格、余额、token 口径、账单聚合或扣费公式。计费负责人可以基于既有 usage 链处理该用途，客服派单代码不得自行计算费用。

## 11. 数据与兼容

DDL 继续通过 AutoMigrate，兼容 SQLite 和 MySQL：

- `AgentTeam.DispatchMode`，默认 `rule`。
- `Conversation.DispatchWeight`，默认 1。
- `ConversationAssignment.DispatchMode`。
- `ConversationAssignment.DecisionConfidence`。
- `ConversationAssignment.WorkloadWeight`，默认 1。

没有新增 DML migration、路由、WebSocket payload 或权限码。旧 Assignment 的空派单方式只代表历史数据缺少该快照；新建人工 Assignment 会在 service 层规范为 `manual`。

丽斯未来测试租户的三个业务客服组使用智能模式，并在现有租户模型授权中增加 `dispatch_decision_llm` 用途；默认综合组保持规则模式。Seed 不复制模型密钥。

## 12. 明确不做

本阶段不实现：

- 自动把已分配会话从忙客服手中抢走或跨组重分配。
- 让模型绕过权限、排班、容量、服务范围或租户隔离。
- 新建独立派单任务表、派单页面、派单权限体系或计费体系。
- 基于向量库的长期客服能力画像；当前连续性只读取该客户的历史 Assignment。
- 完整派单质量报表和组长覆盖率分析；Assignment 和事件已保留后续统计证据。

这些边界保证第一版智能派单可控、可解释、可降级，并能在现有客服组、排班、小组、会话和租户架构中独立回滚。

## 13. 验证

核心自动化覆盖：

- 多租户待派队列轮转和单租户顺序。
- 紧急与等待任务优先级。
- 合法模型选择、严格 JSON、格式重试和规则降级。
- 单候选和明显负载差距直接规则派发，不产生模型调用。
- 公平候选带排除过载客服，提交前仍执行公平保护。
- 模型判断期间新消息导致的过期结果拒绝。
- 事务内容量、完整班次负载快照和当前小组成员资格复核。
- 释放任务和全局待派任务进入实时防抖队列。
- RouteState 更新失败时 Assignment、Conversation 和事件整体回滚。
- 当前加权负载、本班累计权重和连续消息压力。
- 人工转接、规则派单、小组排班和租户隔离原有路径。
- 派单表格桌面列不重叠，移动端只在表格容器内横向滚动，不撑宽页面。
