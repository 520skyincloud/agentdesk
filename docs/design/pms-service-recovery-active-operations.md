# PMS、服务补救与主动经营

## 当前真实链路

企微客户消息仍走现有回复链路：

```text
消息收敛 → Intent → 知识检索/Judge → Generate（必要时调用只读工具）→ Commit → Outbox
```

PMS 查询已注册为现有静态工具 `builtin/pms_query`，不新增 Agent 或并行回复链路。
但截至 2026-09-14，企微员工号 `BuildRuntimeAIAgent` 的工具允许列表只有
`builtin/get_weather`，注册器会过滤 PMS 工具。因此配置开启、客户端接口可调用，
不等于真实企微会话已经能够查询 PMS。

## PMS 能力边界

当前客户端实现 HPMS 文档确认的查询接口，并从服务端 PMS 配置注入 `hotelId`：

- 预订单详情
- 接待单详情
- 按手机号或会员编号/协议公司编号查询当前有效预订单
- 按手机号或会员编号/协议公司编号查询当前有效接待单
- 换单续住候选分页查询
- 实时房态
- 房情库存

当前有效订单查询按补充文档使用原有两个 `detailByPhone` 接口：`phone` 和
`customerNo` 均为可选，但至少传一个；文档要求两者同时传入时由 PMS 做精确组合匹配。
`customerNo` 表示会员编号或协议公司编号。该查询只作为测试环境的业务查询条件，
不代表客户身份已验证；渠道订单号综合搜索、房间属性和普通改房/排房/换房/延迟
退房接口仍未提供，因此只保留未来 Adapter 边界，不注册为可执行工具。

2026-09-14 测试 PMS 的实际响应尚未符合该补充文档：两个接口仅传 `customerNo`
均返回业务码 400、`请求参数不正确:手机号码不能为空`；已知手机号加不匹配的
`customerNo` 查询接待单仍返回该手机号的原订单。客户端参数已接通，但上游会员编号
筛选和组合匹配尚未生效，不能标记为真实可用，也不能依赖它进行订单归属验证。

续住是本轮唯一受控写操作：工具先保存 10 分钟有效的续住预览，只有客户在同
一会话发送明确确认后，服务端才调用文档中的 `renew` 接口，并发起接待单回读。
当前回读仅判断查询接口是否成功，没有比较日期、房号、状态、费用或原单续住产生的新单，
因此还不是完整的执行结果核验。`allowWrite=false` 时写请求会被拒绝；单条操作记录
有防重逻辑，但不能替代同一接待单跨会话互斥、PMS 并发保护和超时后结果核实。

接口地址、认证信息和酒店 ID 从 `pms` 配置读取，也支持环境变量覆盖。工具结果会删除 Token、密码、身份证等敏感字段。

白名单、实名认证、会员资料查询、渠道订单号综合搜索、房间属性、排房、
换房、改房型、延迟退房、改价明细和独立写操作结果查询接口，当前没有足够的
接口文档，代码不会猜测实现。

生产写操作由 `allowWrite=false` 默认关闭。续住记录存放在独立的
`PMSOperation` 表中，不占用人工路由的 `pending_action`；它保存来源消息、预览、
确认消息、幂等键和执行/回读结果。未来其他写操作也必须经过订单归属验证、权限、
幂等键、版本校验、并发检查、执行后读回和审计。

## 服务补救

现有 Ticket/TicketProgress/人工路由继续作为真实执行闭环：

```text
知识优先回答 → 无法解决才建单或转人工 → 分派 → 进展通知 → 完成后恢复 AI
```

`ServiceRecoveryCase` 具备补偿申请和幂等记录的基础结构，当前没有接入对话中的自动补救执行入口。
按当前用户范围，不要求维修 SLA、真实发券或退款赔偿执行；有正式规则依据的补偿承诺仍需
接通规则读取和会话调用，不能把订单金额直接视为补偿授权，也不能声称已经到账。

## 主动经营

`CustomerEngagementProfile` 保存客户同意、退订、偏好和触达频次；`ProactiveReachout` 保存可审计的触达草稿和幂等键。

未获得客户同意、已退订或触达频控未通过时不得发送。没有会员、优惠券、积分或营销平台接口时，只生成内部草稿，不向客户承诺权益，也不自动发营销消息。

当前主动经营仅有上述基础 service 和数据结构，没有会员资料读取、生日事件触发、规则匹配和
实际触达的完整调用入口，不能把草稿接口存在等同于自动经营已上线。
