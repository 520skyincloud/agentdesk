# PMS、服务补救与主动经营

## 当前真实链路

企微客户消息仍走现有回复链路：

```text
消息收敛 → Intent → 知识检索/Judge → Generate（必要时调用只读工具）→ Commit → Outbox
```

PMS 查询作为现有静态工具 `builtin/pms_query` 挂载，不新增 Agent 或并行回复链路。

## PMS 能力边界

当前代码只调用 HPMS 文档确认的查询接口，并按门店配置注入 `hotelId`：

- 预订单详情
- 接待单详情
- 按手机号或会员编号/协议公司编号查询当前有效预订单
- 按手机号或会员编号/协议公司编号查询当前有效接待单
- 换单续住候选分页查询
- 实时房态
- 房情库存

当前有效订单查询使用原有两个 `detailByPhone` 接口：`phone` 和
`customerNo` 均为可选，但至少传一个；两者同时传入时由 PMS 做精确组合匹配。
`customerNo` 表示会员编号或协议公司编号。该查询只作为测试环境的业务查询条件，
不代表客户身份已验证；渠道订单号综合搜索、房间属性和普通改房/排房/换房/延迟
退房接口仍未提供，因此只保留未来 Adapter 边界，不注册为可执行工具。

续住是本轮唯一受控写操作：工具先保存 10 分钟有效的续住预览，只有客户在同
一会话发送明确确认后，服务端才调用文档中的 `renew` 接口，并读取接待单核对
结果。`allowWrite=false` 时任何写请求都会被拒绝；重复确认复用已记录结果，
不会再次提交。

接口地址、认证信息和酒店 ID 从 `pms` 配置读取，也支持环境变量覆盖。工具结果会删除 Token、密码、身份证等敏感字段。

白名单、实名认证、会员 ID 综合订单搜索、渠道订单号综合搜索、房间属性、排房、
换房、改房型、延迟退房、改价明细和独立写操作结果查询接口，当前没有足够的
接口文档，代码不会猜测实现。

生产写操作由 `allowWrite=false` 默认关闭。续住记录存放在独立的
`PMSOperation` 表中，不占用人工路由的 `pending_action`；它保存来源消息、预览、
确认消息、幂等键和执行/回读结果。未来其他写操作也必须经过订单归属验证、权限、
幂等键、版本校验、并发检查、执行后读回和审计。

## 服务补救

现有 Ticket/TicketProgress/人工路由继续作为真实执行闭环：

```text
知识优先回答 → 无法解决才建单或转人工 → 分派 → 进展通知 → 完成后恢复 AI
```

`ServiceRecoveryCase` 记录补偿申请、审批状态、幂等键和外部引用，但不调用不存在的券、升房、延退或赔付系统。

## 主动经营

`CustomerEngagementProfile` 保存客户同意、退订、偏好和触达频次；`ProactiveReachout` 保存可审计的触达草稿和幂等键。

未获得客户同意、已退订或触达频控未通过时不得发送。没有会员、优惠券、积分或营销平台接口时，只生成内部草稿，不向客户承诺权益，也不自动发营销消息。
