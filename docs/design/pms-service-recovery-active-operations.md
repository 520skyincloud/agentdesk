# PMS、服务补救与主动经营

## 当前真实链路

企微客户消息仍走现有回复链路：

```text
消息收敛 → Intent → 知识检索/Judge → Generate（必要时调用只读工具）→ Commit → Outbox
```

PMS 查询注册为现有静态工具 `builtin/pms_query`，不新增 Agent 或并行回复链路。
2026-09-15 修复企微员工号 `BuildRuntimeAIAgent` 的工具允许列表，保留天气并加入
PMS 只读工具；仍由服务端 PMS 配置控制启用。会员问题的 Intent 和混合问题工具筛选
保留 PMS 调用，不要求先从 FAQ 找到会员信息。发布和真实验收记录见本文末尾。

## PMS 能力边界

当前客户端实现 HPMS 文档确认的查询接口，并从服务端 PMS 配置注入 `hotelId`：

- 预订单详情
- 接待单详情
- 按手机号或会员编号/协议公司编号查询当前有效预订单
- 按手机号或会员编号/协议公司编号查询当前有效接待单
- 换单续住候选分页查询
- 实时房态
- 房情库存
- 按手机号查询会员基础信息
- 按真实会员等级 ID 或其兼容编码查询权益及升级/保级规则

会员查询按《会员开放查询 API》(2026-09-14) 接入：
`/admin-api/member/open/members/info/by-phone` 只传 `phone`，
`/admin-api/member/open/members/benefits/by-grade` 只传 `gradeId/gradeCode`。
两条接口均不接受 `tenantId` Query，也不注入酒店参数，租户边界来自服务端认证上下文。
查当前客户权益时先取得会员记录，再使用实际返回的 `gradeId`，不猜测中文等级对应编码。
库存接口则按其既有协议，从配置的 `tenant-id` 补充必需的 `tenantId` Query；
模型不能指定或覆盖该租户。

当前有效订单查询按补充文档使用原有两个 `detailByPhone` 接口：`phone` 和
`customerNo` 均为可选，但至少传一个；文档要求两者同时传入时由 PMS 做精确组合匹配。
`customerNo` 表示会员编号或协议公司编号。该查询只作为测试环境的业务查询条件，
不代表客户身份已验证；渠道订单号综合搜索、房间属性和普通改房/排房/换房/延迟
退房接口仍未提供，因此只保留未来 Adapter 边界，不注册为可执行工具。

2026-09-14 测试 PMS 的实际响应尚未符合该补充文档：两个接口仅传 `customerNo`
均返回业务码 400、`请求参数不正确:手机号码不能为空`；已知手机号加不匹配的
`customerNo` 查询接待单仍返回该手机号的原订单。客户端参数已接通，但上游会员编号
筛选和组合匹配尚未生效，不能标记为真实可用，也不能依赖它进行订单归属验证。

现有续住 service 能保存 10 分钟有效的预览，客户在同一会话明确确认后可调用
`renew` 并发起接待单回读，但该代码存在以下尚未完成的安全边界。
当前回读仅判断查询接口是否成功，没有比较日期、房号、状态、费用或原单续住产生的新单，
因此还不是完整的执行结果核验。`allowWrite=false` 时写请求会被拒绝；单条操作记录
有防重逻辑，但不能替代同一接待单跨会话互斥、PMS 并发保护和超时后结果核实。

本轮客服工具明确限制为只读 action，Schema 和执行入口均不再开放续住预览/提交。
即使测试配置 `allowWrite=true`，也不能经该工具新建写操作。既有续住 service、
历史操作记录和配置不被修改；不能将本次查询接通描述为续住闭环完成。

接口地址、认证信息和酒店 ID 从服务端 `pms` 配置读取，也支持环境变量覆盖。
会员响应按文档字段白名单返回，保留长 ID、金额精度、空值和状态；
实接口成功码为 `200`、`tenantId` 为十进制字符串，兼容文档示例 `code=0` 和数字 ID，
不将 ID 转换为浮点数。
`gradeRule` 未完整公开的子字段不猜测实现，完整可读规则以接口摘要为准。
冻结/挂失、等级停用或 `gradeAvailable=false` 不解释成可使用权益。
会员有效结束时间为空不自行推导永久有效；权益配置不等于实际订单报价或履约。
PMS 工具 Trace 只保留 action、状态、耗时等诊断，不记录查询参数原值、原始结果和错误。
客户工具输出按订单、房态、库存各自字段白名单投影，不把整店住客名单和电话交给模型；
内部 service 的原始查询数据保留，不因客户侧脱敏破坏既有回读逻辑。
客户主动发送的原始聊天消息继续沿用既有消息存储，不属于新增 API 业务日志。

白名单、实名认证、渠道订单号综合搜索、房间属性、排房、
换房、改房型、延迟退房、改价明细和独立写操作结果查询接口，当前没有足够的
接口文档，代码不会猜测实现。

生产写操作由 `allowWrite=false` 默认关闭。续住记录存放在独立的
`PMSOperation` 表中，不占用人工路由的 `pending_action`；它保存来源消息、预览、
确认消息、幂等键和执行/回读结果。未来其他写操作也必须经过订单归属验证、权限、
幂等键、版本校验、并发检查、执行后读回和审计。

## 服务补救

现有 Ticket/TicketProgress/人工路由继续作为真实执行闭环：

```text
知识优先回答 → 无法解决才建单或转人工 → 分派 → 进展通知 → 完成后恢复 AI
```

`ServiceRecoveryCase` 具备补偿申请和幂等记录的基础结构，当前没有接入对话中的自动补救执行入口。
按当前用户范围，不要求维修 SLA、真实发券或退款赔偿执行；有正式规则依据的补偿承诺仍需
接通规则读取和会话调用，不能把订单金额直接视为补偿授权，也不能声称已经到账。

## 主动经营

`CustomerEngagementProfile` 保存客户同意、退订、偏好和触达频次；`ProactiveReachout` 保存可审计的触达草稿和幂等键。

未获得客户同意、已退订或触达频控未通过时不得发送。没有会员、优惠券、积分或营销平台接口时，只生成内部草稿，不向客户承诺权益，也不自动发营销消息。

现有查询已补会员基础信息、等级权益及规则读取；新接口没有客户生日日期、历史消费或
入住记录，也不执行发券和积分入账。主动经营尚缺生日事件触发、规则匹配和实际触达的
完整调用入口，不能把会员资料可查或草稿接口存在等同于自动经营已上线。
