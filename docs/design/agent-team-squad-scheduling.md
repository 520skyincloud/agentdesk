# 综合客服组、客服小组与排班联动设计

> 状态：当前实现依据（2026-07-21）
>
> 当前负责分支：`codex/tenant-ai-integration`
>
> 派单细节：`docs/design/conversation-dispatch-engine.md`

## 1. 组织语义

```text
Tenant
  -> 综合客服组 AgentTeam
       -> 客服小组 AgentTeamSquad
            -> 小组成员 AgentTeamSquadMember
       -> 排班 AgentTeamSchedule
```

- 综合客服组负责业务责任、门店员工号服务范围、组长、任务池和派单模式。
- 客服小组只负责组内人员组合，用于白班、晚班、机动班等，不独立绑定门店员工号。
- 排班决定某个时间段由全组或一个客服小组值班。
- Presence 决定计划值班人员此刻是否实际可接单。
- 会话始终只归属一个综合客服组；小组只作为 Assignment 的班次快照。

当前阶段一个客服档案只属于一个综合客服组，但可加入该组内多个小组。门店员工号也只归属一个综合客服组，不固定绑定某位客服。

## 2. 数据模型

### 2.1 AgentTeam

关键字段：

- `TenantID`
- `LeaderUserID`
- `DispatchMode`：只允许 `manual/rule`
- 门店和企微员工号范围
- `Status`

历史 `intelligent` 在 Migration 64 中统一转为 `rule`。客服组页面不再提供模型派单选项。

### 2.2 AgentTeamSquad

- `TenantID`
- `TeamID`
- `Name`
- `LeaderUserID`，可为空
- `Status`
- `Remark`

同一综合客服组内小组名称唯一。小组不能迁移到其他综合客服组；需要调整时，应先清理相关排班再重建。

### 2.3 AgentTeamSquadMember

- `TenantID`
- `SquadID`
- `AgentProfileID`
- `Status`

成员必须属于该小组对应的综合客服组。同一客服可以加入多个本组小组，不能借小组关系跨综合组服务。

### 2.4 AgentTeamSchedule

- `TenantID`
- `TeamID`
- `SquadID`：`0` 表示全组值班，正数表示指定小组
- `IncludedAgentProfileIDs`：本班临时替班人员
- `ExcludedAgentProfileIDs`：本班请假或临时移出人员
- `StartAt / EndAt`
- `Remark / Status`

临时加入和排除保存客服档案 ID，均要求客服仍属于该综合客服组。排除优先于小组成员；加入只在指定小组班次中补充非小组成员，全组班次本来已包含全组人员。

### 2.5 ConversationAssignment

`SquadID` 固化派发时采用的小组快照。客服后来退出小组或班次结束，不修改历史 Assignment。

## 3. 排班约束

### 3.1 时间约束

- 单条班次结束时间必须晚于开始时间。
- 单条班次最长 24 小时。
- 支持跨自然日，例如 `22:00 -> 次日 08:00`。
- 不能新增或修改历史日期班次。
- 同一小组同一时间只允许一条有效班次；全组班次不能与该综合组任何班次重叠。
- 同一综合组的不同小组允许短时重叠，用于白班/晚班或专项小组交接；运行时会合并有效窗口并去重同一客服。
- 批量请求内部和数据库已有班次都按上述小组/全组语义检查冲突。

“一天多个班次”由多条不重叠 Schedule 表达，例如早班、午间空档和晚班。系统不新增重复的班次规则表。

### 3.2 人员约束

- 指定小组必须启用且属于所选综合客服组。
- 临时加入/排除人员必须属于该综合客服组。
- 同一客服不能在一个班次同时被加入和排除。
- 单个班次加入和排除各不超过既有安全上限。
- 保存时至少有一名启用且可接待的客服，否则拒绝。

规则组的覆盖计算还要求 `AutoAssignEnabled=true` 和有效并发上限；人工组只要求可人工接待，不强制开启自动接单，也不把自动派单并发上限当作人工值班门槛。两种模式都要求 User、AgentProfile 启用且账号同时具备 `conversation.view` 与 `conversation.send`，因此预览不会出现“显示有人、实际无权回复”的假覆盖。

### 3.3 覆盖风险

预览和保存时计算：

- 可接待客服人数。
- 配置总并发容量。
- 零人员阻断。
- 仅一人值班的单点风险提醒。

覆盖预览检查账号、档案、回复权限及派单模式对应的配置资格，不伪装为实际在线人数。规则模式的实际可接单仍由运行时 Presence、剩余容量和服务范围继续收紧；人工模式允许主管在保留审计理由的前提下覆盖排班、Presence 和自动容量，但不能覆盖租户、客服组、账号、权限或服务范围。

## 4. 班次人员集合

规则组当前班次候选集合按以下顺序产生：

```text
全组班次：综合组启用客服
小组班次：小组启用成员
  + IncludedAgentProfileIDs
  - ExcludedAgentProfileIDs
  -> User/Profile 启用
  -> 自动接单与容量有效
  -> 会话查看/回复权限
  -> 门店/员工号服务范围
  -> Presence 为 online/idle 且三分钟内活跃
  -> 未达到最大并发
```

指定小组无人可用时，任务留在综合组待派池，不静默扩大到全组。需要临时补位应使用本班“替班人员”，确保主管意图和审计一致。

## 5. 班次交接

班次变化会触发两个动作：

1. 重新消化该综合组的待派队列。
2. 检查尚未人工首响的规则 Assignment，以及客户追问超时后原客服硬不可用的 Assignment。

以下情况可在首响前重派或释放：

- 原客服已离线、休息或退出自动接单。
- 原客服不再属于当前班次/小组。
- 账号、档案、权限、客服组或服务范围失效。
- 超过首响 SLA 且有更合适的合法替代人。

已有人工回复的会话不因班次结束立即转走。只有客户仍有未回复追问、超过 Response SLA，且原客服已离班或发生其他硬不可用时，才在原综合组内自动接力；忙碌、负载或容量调整不触发该动作。主管仍可使用现有转派动作主动交班并填写原因。

恢复链路包含事务内消息/状态复核、90 秒候选冷却和最多三次自动重派，防止班次边界或网络抖动导致会话来回跳转。达到上限后释放到人工编排池并通知主管，不继续自动动作。

## 6. 页面职责

### 6.1 客服档案页

保留三个既有视图：

```text
[客服成员] [小组编排] [服务范围]
```

- 客服成员：账号对应的客服档案、综合组、容量、自动接单和优先级。
- 小组编排：左侧综合组全部客服，右侧小组容器。
- 服务范围：综合组纳管的门店员工号，不复制用户管理的事实源。

小组编排继续支持拖拽和批量加入。拖拽预览使用页面级 `DragOverlay`，避免客服条目被左侧滚动容器裁切；加入小组不会从综合组成员池移除。

### 6.2 排班页

单条排班顺序：

```text
综合客服组 -> 客服小组（可选） -> 替班/请假 -> 开始时间 -> 结束时间
```

批量排班支持：

- 多个综合客服组。
- 日期范围和星期。
- 一天多个时间段。
- 跨午夜时段。
- 单组场景下指定小组和替班/请假。
- 生成前预览冲突、人数、容量和风险。

当指定小组或临时人员时只能选择一个综合客服组，避免同一份人员 ID 被错误应用到其他组。

### 6.3 派单工作台

客服负载区展示：

- 实际 Presence 和最近活跃时间。
- 是否在当前班次/小组。
- 当前会话、待首响、待回复和加权压力。
- 本班累计工作量。
- 不可自动接单的明确原因。

排班页面负责计划，派单页负责实时运行，客服会话页负责回复；三者不相互复制配置。

## 7. 权限和数据范围

- 查看小组复用 `agentTeam.view`。
- 创建小组复用 `agentTeam.create`。
- 编辑成员、负责人和状态复用 `agentTeam.update`。
- 删除小组复用 `agentTeam.delete`。
- 排班继续使用 `agentTeamSchedule.view/create/update/delete`。

所有接口继续经过 `AgentTeamScopeService`：公司主管管理本租户全部综合组，组长只管理负责组，普通客服不能修改组织和排班。没有小组专属隐藏权限。

## 8. 实际排班方法

建议主管按以下方式运营：

1. 把长期稳定人员编成白班、晚班和机动小组。
2. 用批量排班一次生成一周或一个周期，不逐日重复录入。
3. 每个班次保留至少两名可接单客服，单人班只作为有明确兜底的例外。
4. 按历史峰值估算“人数 x 合理并发”，并留出休息、投诉和复杂任务余量。
5. 请假用排除，临时顶班用加入，不为了单日变化修改长期小组。
6. 交班人员提前登录，新班次开始后 Presence 才会进入候选；不能只依赖排班表。
7. 通过派单页观察待首响、待回复和本班债务，不只看当前会话数量。
8. 高峰积压时优先增加值班人员；提高单人最大并发只适用于任务确实较轻的场景。
9. 无人班、单点班和容量不足应在发布排班前解决，不把风险留给运行时告警。

## 9. 兼容和迁移

- 历史 `SquadID=0` 排班继续表示全组值班。
- 新增 Include/Exclude 字段由 AutoMigrate 建立，SQLite/MySQL 均使用逗号分隔 ID 的兼容存储方式。
- `AgentProfile.TeamID`、`StoreStaffBinding.AgentTeamID`、`WxWorkProtocolInstance.AgentTeamID` 和 `Conversation.CurrentTeamID` 语义不变。
- `AgentProfile.ServiceStatus`、`ReceiveOfflineMessage`、`LastStatusAt` 已退役；Presence 是实际状态事实源。
- 已有 Assignment 和班次历史不因成员调整回写。

## 10. 不做的复杂化

当前不实现：

- 客服跨综合客服组多归属。
- 门店员工号同时绑定多个综合客服组。
- 小组独立权限、服务范围、任务池和派单算法。
- 固定轮班模板或自动循环规则表；当前批量生成已覆盖周期录入。
- 因负载、忙碌或更优候选对已回复会话自动抢单；追问超时且原客服硬不可用的有界接力除外。
- 用排班记录代替 Presence 或考勤事实。

## 11. 验证

重点覆盖：

- 小组成员必须属于综合组，允许本组多小组归属。
- 全组班次、小组班次、替班、请假和优先排除。
- 单条/批量重叠、跨午夜、多个日内时段和历史日期校验。
- 人工组与规则组不同覆盖口径。
- 零人员阻断与单点风险。
- 班次变化后队列重派、未首响恢复和追问超时硬失效接力。
- 组长范围、租户隔离和页面字段一致。
